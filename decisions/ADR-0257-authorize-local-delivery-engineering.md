# ADR-0257 — Authorize engineering scope `local_delivery` (W1), by explicit operator instruction

- **Status:** **Accepted** (operator, 2026-11-23, explicit instruction in chat; not delegation). Authorizing an engineering scope is a decision of the operator, not a review result and not a delegation. The operator's instruction was conditional: authorize each remaining scope that is part of the design and aligns with the constitution. This ADR records that check for this scope.
- **Date:** 2026-11-23
- **Authorizes:** engineering scope `local_delivery` only. No other scope changes state through this ADR.
- **Depends on:** the scopes named in `depends_on` for `local_delivery` in the repository contract, already authorized.
- **Waives:** the **pre-engineering** phase of gate V-024 for engineering purposes only. Its pre-release phase is untouched and stays open.

## Context

`local_delivery` (W1) is part of the complete, audited design and its scope contract exists in [`engineering_scope_contracts.json`](../machine/engineering_scope_contracts.json). Constitution check: C-15 (an accepted relationship needs no discovery infrastructure; a local resolver may use LAN rendezvous) and C-16 (no surveillance mechanism). The design queue has no open blocking item for it. The unlock contract ([`RELEASE_WAVES_AND_SCOPED_ENGINEERING_UNLOCK.md`](../docs/process/RELEASE_WAVES_AND_SCOPED_ENGINEERING_UNLOCK.md) section 5) otherwise requires every gate that lists the scope to have `pre_engineering_status` passed or waived by an ADR. Gate V-024 still has criteria open: the real-browser feasibility result (a host-local ordered, reliable WebRTC DataChannel passing the frame and backpressure tests, or an explicit `local_delivery` unavailable capability result on that runtime) and independent review; the frozen [`lan.cddl`](../spec/cddl/lan.cddl) with two-codec vectors, the passive-observer trace model and the offline first-contact model are met, and V-003 and V-015 pre-engineering have passed. The operator may choose to authorize engineering now and keep that evidence as a release obligation. This is the same shape as ADR-0250, ADR-0217 and ADR-0183.

## Decision

1. **`local_delivery` is authorized**, by explicit operator instruction. Engineers follow [`ENGINEER_START_HERE.md`](../docs/process/ENGINEER_START_HERE.md), the `local_delivery` entry of [`engineering_scope_contracts.json`](../machine/engineering_scope_contracts.json) and the design gate in [`AGENTS.md`](../AGENTS.md).
2. **What the scope covers.** the offline-local LAN message and file delivery binding frozen by ADR-0158 (`LanDeliveryProfile-v1`): LAN rendezvous for marked contacts, sealed delivery over a host-local channel, offline first contact through the local IntroGate adapter, and the capability row that reports `local_delivery` unavailable where a runtime cannot meet it. Sources: [`LAN_RENDEZVOUS_AND_OFFLINE_LOCAL_MODE.md`](../docs/architecture/network/LAN_RENDEZVOUS_AND_OFFLINE_LOCAL_MODE.md), [`SEALED_SENDER_DELIVERY_PROFILE.md`](../docs/architecture/delivery/SEALED_SENDER_DELIVERY_PROFILE.md), [`MULTI_RELAY_AND_DELIVERY_RESILIENCE.md`](../docs/architecture/delivery/MULTI_RELAY_AND_DELIVERY_RESILIENCE.md).
   - **Not covered:** any clear-sender or weaker browser-only fallback, any LAN identity or relationship authority, and any change to BlobID or ciphertext digest identity. Each needs its own ADR.
3. **Gate V-024 pre-engineering is waived by this ADR, for engineering only.**
   - *Risk accepted:* LAN delivery code can be written before real-browser feasibility is shown and before independent review, so a runtime might be found unable to carry the channel after code exists, and an unreviewed rendezvous construction could leak linkage.
   - *Compensating controls:* (a) the first build slice freezes this scope's wire objects (CDDL, registered numeric fields and domain-separation labels, positive and negative vectors, two independently written codecs agreeing) before any other product code, by the V-005 method, additively and under ADR-0165; (b) the feature is built behind a capability flag that is off in every release until the release evidence below is in, and no production build offers it; (c) every construction the design leaves open is written in an ADR by delegation that does not amend audited text, and where the design is silent the engineer writes the question in the scope's plan and stops; (d) no wire requirement is added to an earlier wave beyond the reserved extension and criticality points already frozen in V1 semantics (RELEASE_WAVES rule 1); (e) where the channel binding is unavailable the capability row reports `local_delivery` unavailable and delivery never falls back to a weaker path; (f) rendezvous state is ephemeral and regenerated, never restored as durable authority; LAN presence never creates relationship or device eligibility.
4. **Still required BEFORE RELEASE, not before engineering.** two independent implementations interoperating over a real LAN, including a browser client where the capability row claims support; any release offering LAN delivery, declaring `local_delivery`, or claiming offline-local delivery needs them. `om-open-beta-1` does not list `local_delivery` and stays as it is. Authorization is not release: nothing here edits a public release declaration.
5. **Constraints.** No new cryptographic primitive and no weakened floor (C-20); no mandatory third-party service and no project-operated service for this scope (C-01); no design change. Where the design is silent the engineer writes the question in the scope's plan and stops, or an ADR by delegation records a construction that does not amend audited text. The first deliverable for the scope is a build plan that states which design documents were read.
6. **Where did authority go?** Nowhere new. A LAN peer is only a route to an already authorized relationship; presence on a network establishes nothing.

## Consequences

- The review basis becomes the operator's decision, not independent review. The open independence criteria of V-024 move to the release obligations in point 4.
- The first slice is design-bound specification and test work (wire freeze and the evidence harness named above); no feature code is reachable in any build until the capability flag is turned on by a later, evidenced decision.
