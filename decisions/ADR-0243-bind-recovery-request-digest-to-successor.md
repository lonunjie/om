# ADR-0243 — Exact recovery-request identity bound by the recovery-signed successor

- **Status:** Proposed, needs specialist metadata judgement and operator acceptance (2026-11-19). Not accepted by delegation: it adds a new critical W0 extension, is classified critical protocol evolution (ADR-0165), and introduces a public correlation between an ACS child and a recovery-request digest, which a delegated ADR may not do against the metadata floor. Enablement blocked. **Safe fallback in force meanwhile:** no positive older-sheet (`saved_sheet_older_than_recovery`) classification on a recovery link whose original request cannot be shown from independent evidence; on such links the outcome stays `needs_evidence`, a veto is matched only against the request digest the verifier itself observed, and no "any valid matching request" reading is used. Audited W0 text is untouched.
- **Date:** 2026-11-19
- **Decided by:** the operator is to decide; nothing here is decided by delegation. Authored by an independent reviewer of a different vendor than the code author; imported by the repository's agent as a proposal, with the changes listed under "Import notes".
- **Class:** **Incompatible critical-extension evolution** for newly created recovery successors (ADR-0165), not an additive noncritical field or an editorial correction. The frozen W0 numeric ACS fields and existing signature/hash labels are not repurposed. Historical W0 recovery successors retain their historical meaning, but cannot satisfy the stronger sheet-only dossier identity claim without independent pre-existing evidence.
- **Answers:** which exact recovery request a recovery-signed successor stands for, for veto matching and older-sheet classification (`RK2A-02`, `RK2A-03`).

## Problem and decision

`RecoveryRequest` key 7 authenticates a 16-byte nonce under `OM-RECOVERY-REQUEST-SIG-v1`. The recovery-role signature on the existing W0 successor authenticates **the ACS child body**, not the request or its nonce. The RecoveryRecord dossier key 5 and the index bind the child hash but are AEAD-authenticated by a RecoveryRoot/Kit holder, who can replace their own dossier entries. Thus a second legitimately root-signed `RecoveryRequest` with all fields equal except the nonce has a **different** `OM-RECOVERY-REQUEST-HASH-v1` digest and different veto identity, yet is accepted by the non-time `verify_recovery_successor` check for the unchanged child; a fixture exercises this case. **Reject the “any valid matching request” interpretation for exact historical-request assertions.** In particular, never declare that a veto for digest A was checked against the *actual* original recovery child if the supplied dossier could replace A with B.

For **new** recovery successors under this extension, the recovery-signed child MUST itself commit the **digest value of the exact canonical unsigned RecoveryRequest body that originated that successor**. Add a new **critical** extension to the child's existing W0 `AccountControlState` key 23; its value is `digest {0:1, 1:bstr32}` computed using the existing `OM-RECOVERY-REQUEST-HASH-v1` over the canonical unsigned request body, including the nonce. The W0 recovery-role signature already authenticates every byte of the child body, including this extension. A child with a different nonce would need **a different signed child body and a different ACS hash**; a root holder cannot change the committed request digest on an unchanged child by rewriting the RecoveryRecord dossier. Verify the signed request normally, recompute its digest and compare in constant time to the child's critical extension *before* using the dossier for `saved_sheet_older_than_recovery`, for veto matching, or for a new recovery-successor acceptance under this evolution. A second signature over the **same canonical request body** has the same semantic digest and does not create a new request identity. Exactly one digest is committed; no alternative requests or multi-valued witness map.

The sender persists the exact signed request, its digest, target credential, unsigned child body including this extension and subsequent signed child **atomically before publication**. Retries reuse those bytes and do not re-nonce the request. The key-5 dossier continues carrying the exact signed request envelope; it is cross-checked against the child commitment rather than trusted merely because AEAD opens. A late/missing/duplicate or different-digest dossier is `needs_evidence` if its authenticated bytes are unavailable, `integrity_failure` if a supplied request contradicts a verified signed child; neither yields `saved_sheet_older_than_recovery`. No sheet-only device is allowed to borrow another device's timer or veto-completeness observation. A known verified veto for the committed digest remains terminal under the original W0 rules.

For a **historical** recovery child without this new extension, do not mutate its old signed bytes or retroactively call the nonce cryptographically bound. A sheet-only reader attempting the stronger ADR-0238 classification must return **`needs_evidence`** unless it already has independent, previously authenticated evidence linking the original request digest to that signed child under the existing ADR-0202 controller-approval ceremony or its own historical durable verifier state. Any such alternative must be explicitly specified and independently verified; a sender's new receipt signed only with the same RecoveryRoot after the fact is **not** independent historical evidence. Historical normal W0 verification and already accepted pins are not invalidated solely by this proposal. New child emission and cross-version behavior remain gated.

## Exact CDDL / critical-extension registration

```cddl
; account.cddl W0 AccountControlState retains its existing ? 23: extensions.
; New registered critical extension in that map, ONLY on a recovery-signed child:
; "om.critical.acs.recovery_request_ref.v1": {
;   0: true,                ; critical
;   1: {0: 1, 1: bstr .size 32} ; digest: SHA-256 under OM-RECOVERY-REQUEST-HASH-v1
; }
;
recovery-request-ref-extension = {
  0: true,
  1: digest,
}
; Semantic: exactly one extension key above on each new-profile recovery child;
; its digest equals RecoveryRequest::digest() of the exact signed request's body.
; Legacy without extension is NOT a positive sheet-only exact-request proof.
```

Register the exact extension ID, version `v1`, owner `AccountControlState`, criticality `true`, canonical payload, and fail-closed rule in [`om-numeric-fields.json`](../spec/registries/om-numeric-fields.json) (known extensions) and [`om-cbor-profile.json`](../spec/registries/om-cbor-profile.json); the `om.critical.` prefix makes unknown readers reject the child rather than ignore its authority-changing semantics. **No new domain-separation label**: retain `OM-ACS-SIG-v1`, `OM-ACS-HASH-v1`, `OM-RECOVERY-REQUEST-HASH-v1`, `OM-RECOVERY-REQUEST-SIG-v1`. A builder MUST upgrade `Acs::from_body` / raw-body retention / verifier so it correctly parses key 23 and hashes/signs the **exact original canonical ACS body**; Core does not yet parse key 23 on this object, so the extension needs code changes as well as CDDL and registry changes. Full new-extension interoperability is an explicit protocol-evolution gate, not a transparent v1 patch.

## Conformance vectors

- `RK2C-01`: fixed root key, request nonce A, signed request A, exact request digest A, recovery child with critical extension A and complete real hybrid W0 recovery signature; golden canonical CBOR of request body, signed request, child body, signed child, child hash, dossier and classification `saved_sheet_older_than_recovery` (still restricted, zero elapsed credit).
- `RK2C-02`: same parent, target and policy, root-signed request nonce B, **unchanged A child** and original A child hash: reject as `integrity_failure` despite B's valid signature. Mutation of extension ID/criticality/algorithm/digest, extra request, omission, wrong role and unknown critical extension likewise fail closed.
- `RK2C-03`: a *new* child body carrying B yields a distinct signed hash; a controller that has pinned A's child cannot treat B as the same branch. The old fixture's nonce-substitution success is retained as a **historical negative** demonstrating the absence of exact binding, not promoted to a positive.
- `RK2C-04`: known veto for A, substitute request B, and restarted local timer: A's veto still applies to A, B cannot mask it against child A; new child B independently requires its own verifier-local observations and reconciliation. Show the origin and target never gain authority from a sheet-only classification.

## Metadata, authority, compatibility and audited text

The new digest would be inside the signed ACS child, whose state hash is already shared in head gossip. Anyone able to read the complete child and independently guess/obtain candidate request bodies can now match the child to **one specific request digest**, potentially correlating recovery inbox/board observations and public head history. This is **a real additional metadata linkage** compared with an unbound W0 child: do not claim it is private merely because the RecoveryRecord is encrypted. A Home observing request digests can correlate to a disclosed child carrying the extension. No root, nonce plaintext, inbox capability or policy body is put in the child, but digest equality is observable. Obtain an explicit metadata specialist decision: if this correlation fails the audited metadata floor, **do not enable** this construction; no weaker “same-fields” fallback is authorized.

The **audited W0 shapes need not be edited** because key 23 is already the registered extension carrier; however, **mandatory use of a new critical extension for future recovery success changes accepted/rejected signed-child bytes and cross-version compatibility**. Under ADR-0165 this is **not** an additive-noncritical interpretation or a harmless clarification. Register/approve a new immutable extension lineage with migration, capability negotiation, explicit old-client refusal, formal authority invariants, two independent hybrid-signature codecs and specialist acceptance. If the audit owner instead requires that *all W0 recovery children including historical ones* bind a request digest, **audited verifier semantics must explicitly change** and existing signatures cannot be repaired in place; separate approval/new protocol lineage is mandatory. The present proposal does not grant that approval or relax recovery timer/veto floors.

## Import notes (collision check and edits, 2026-11-19)

- **Values checked, no collision.** W0 key 23 is the existing `extensions` field of `AccountControlState` ([`account.cddl`](../spec/cddl/account.cddl)); no new numeric field is added. The extension id `om.critical.acs.recovery_request_ref.v1` does not appear in [`om-numeric-fields.json`](../spec/registries/om-numeric-fields.json) (known extensions today: `om.acs.fork_ack`, `om.acs.legacy_policy`, ...), [`om-cbor-profile.json`](../spec/registries/om-cbor-profile.json), any CDDL file or any ADR; it uses the `om.critical.` prefix reserved by ADR-0157 for mandatory-to-understand extensions. The existing labels `OM-RECOVERY-REQUEST-HASH-v1` and `OM-RECOVERY-REQUEST-SIG-v1` are reused unchanged. Vector ids `RK2C-01` to `RK2C-04` appear nowhere in the repository. Nothing was registered and no frozen CDDL or registry file was edited.
- **Why proposed, not accepted.** AGENTS "Design gate" rule 6 and the operator's standing direction forbid an ADR by delegation from weakening a cryptographic or metadata floor. This ADR's own metadata section states a real new linkage (a request digest observable at a Home becomes matchable to a disclosed child), and its class is critical protocol evolution. It needs a specialist metadata decision and the operator's acceptance. If the correlation is rejected, the ADR itself says no weaker "same-fields" fallback is authorized.
- **Fallback while proposed.** See the status line: no positive older-sheet classification on ambiguous requests; outcome `needs_evidence`. ADR-0242's walk therefore treats a recovery-signed link as non-classifiable until this ADR is accepted and implemented.
- **Audited text.** Untouched: no W0 shape, verifier rule or Home API text was edited.
- **Edits.** The finding-severity line, the heading "Defect and decision", and two sentences describing current fixture and Core behaviour were reworded neutrally; the status, date and decided-by lines were rewritten (the proposal's own "Decided by" is replaced); this section was added. No ruling text was changed.
