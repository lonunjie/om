## Decision

1. **Independent custody and purpose.** On issuing a *new* safety-code lineage for Maximum Privacy, draw `RelationshipRecoveryKey = CSPRNG(32)` independently of RecoveryRoot, device keys, account seeds and all derived recovery keys. Show two distinct, separately acknowledged written codes; the second recovers only the *encrypted contact reconnect snapshot*. It authorizes no ACS signature, device enrollment, Home write or recovery vote. A missing second code never blocks restoring the account but leaves relationships unrecovered. Do not upload the second code; do not store it in the first sheet, recovery record, cloud backups, logs, crash traces or analytics. Controllers hold it only in their protected RecoveryKit/DeviceVault; the person holds the written code. Re-key on every safety-code replacement, revoke access to the old writer lineage by the existing policy controls, and wipe obsolete local keys as eligibility ends.
2. **Second written format.** Preserve the **non-CBOR** ADR-0203 Recovery Sheet **version 2** layout, checksum algorithm, RFC4648 Base32 sheet/compact form, line checks and QR media from [`spec/protocol/recovery-sheet.md`](../spec/protocol/recovery-sheet.md). Register `version=0x02, kind=0x03` for a relationship secret that **must include the same OwnerRecoveryCheckpoint** as the concurrently written version-2 root sheet. Its 32-byte key substitutes for the `root` field of version-2 kind `0x01` at offsets 2..33. Offsets: `0 version(1) | 1 kind(1) | 2 key(32) | 34 recovery_scope_id(32) | 66 port(2, BE, 0=443) | 68 host_len(1) | 69 host(host_len ASCII) | 69+host_len canonical OwnerRecoveryCheckpoint CBOR(82..90) | final check(4)`. Exact length `73+host_len+checkpoint_len`, with no trailer. Check = first 4 bytes of the digest-value of `DS-HASH(OM-RECOVERY-SHEET-CHECK-v1, body_before_check)`. All v1 host restrictions remain. QR = `om:recover/` + unpadded base64url of these bytes; the kind is checked *before* any key enters a cryptographic operation. Display must literally say **Relationship code (contacts only)**. Kind `0x03` is rejected by the account-root entry and by a place-only parser; kinds `0x01/0x02` are rejected by the relationship-key entry. A legacy 35-byte root-only string or version-1 key string is never interpreted as a relationship key. The person enters the root and, optionally, this second code independently; verify **scope, host, port and exact canonical checkpoint bytes** equal the root sheet to prevent mixing lineages, accounts or Homes. Do not invent a new unregistered cipher or a second QR prefix; the existing tagged QR namespace is already type-disjoint by the kind byte.
3. **Record's second layer.** For Maximum Privacy, use **only** `RecoveryRecord` key 8 (not key 7) once a new lineage has the relationship key: 12 fresh random bytes of AES-256-GCM-SIV nonce followed by ciphertext and 16-byte tag over the canonical `relationship-snapshot` (type from existing [`recovery-record.cddl`](../spec/cddl/recovery-record.cddl)). Use the independently drawn key as the raw 256-bit AEAD key, **not** as an input to RecoveryRoot's HKDF; AAD is the **already frozen** `OM-RECOVERY-RELATIONSHIP-SNAPSHOT-AEAD-AD-v1`: canonical CBOR `[label, recovery_scope_id, record_generation, record_version=1]`. Retain all frozen record-envelope key/nonce/AAD checks and bucket padding. The AEAD opening is not ACS authority: each reconnect route and key is independently revalidated. A wrong or missing relationship code returns a distinct *contacts unavailable* status; it cannot cause fallback to exposing the plaintext snapshot under key 7.
4. **Transition while the second code does not exist.** Existing Maximum Privacy writer's empty `relationship-snapshot` at key 7 is an **interim limited state**, *not* a complete Maximum Privacy backup and never reported as fully “On”. The next confirmed replacement of the safety code creates both new keys, anchor and lineage; only then does the record use key 8. Do not retroactively copy old root-readable relationship data into the new lineage before explicit replacement and the new code's confirmed custody. An old normal-profile record remains independently readable under its older root for the Home's retention, not magically erased; the user is told this limitation.
5. **Checkpoint anchor.** In the device-private RecoveryKit add an optional anchor `{account_id, generation, state_hash}` matching the verified ACS head at *display* time. A v2 written sheet contains exactly this checkpoint. A kit without an anchor retains the genesis rule for older sheets. A writer retains the anchor state and every verified successor while that lineage remains writable. `RecoveryRecord.acs_evidence.anchor_segment` carries the **contiguous signed ACS states starting with the anchor, inclusive, through the state immediately before the oldest tail state**, oldest first; head and tail semantics are unchanged. Verify every successive `previous_state_hash`, matching AccountID/generation/digest, current parent policy, all required signatures and the **exact union of credentials referred to by head, tail and segment**. At most 56 segment states and at most 65 states in the union; existing 320-credential and 1,048,000-byte record bounds remain. No segment splitting, truncation disguised as completeness, or trust in the Home as an authority.
6. **Restore decisions are separate and terminal where appropriate.** Start from the sheet checkpoint; neither demand genesis evidence for a v2 sheet nor trust a head that merely resembles the checkpoint. If the signed chain does not include a needed checkpoint/contiguous link, return `needs_evidence`, remain restricted and allow the existing in-session/contact evidence paths. If the complete verified post-checkpoint chain **crosses an owner-recovery transition for which this fresh sheet-only device lacks its own timed verifier evidence**, return `saved_sheet_older_than_recovery` and stay restricted; do *not* silently downgrade this to `needs_evidence` or use a different route to evade the wait. If the bounded writer cannot include the checkpoint segment, keep a verifiable record but mark status `needs_new_safety_code`, **not** `on`. A `on` status requires an acknowledged current-head record and usable anchor continuity.
7. **Floors and cleanup.** Apply ADR-0225's `(recovery_scope_id, opaque_locator)` durable high-water marks (max 16, refuse insertion at capacity; 400-day cancelled-attempt retention; never silently evict). A new sheet is a new lineage. Earlier epoch inbox draining and old-record delete debt remain ADR-0226/0227 obligations. No decrypted contact data is written to logs or Homes outside the padded recovery AEAD.

## Additive CDDL (reserved by this ADR; not yet in `spec/cddl/recovery-record.cddl`)

```cddl
; In RecoveryKit, after key 10, retaining 0..10 and 23 without renumbering:
  ? 11: recovery-anchor,
recovery-anchor = {
  0: bstr .size 32,                ; AccountID
  1: uint,                         ; verified ACS generation
  2: bstr .size 32,                ; OM-ACS-HASH-v1 digest-value
}
; In recovery-acs-evidence after existing keys 0..3:
  ? 4: [0*56 bstr .cbor signed-AccountControlState], ; anchor_segment
; Exactly one of RecoveryRecord keys 7/8 is allowed; key 8's plaintext
; MUST decode to the existing relationship-snapshot CDDL.
```

The new sheet kind is a **byte layout, not CDDL**. Register the two optional field numbers and the `0x03` sheet kind in the appropriate frozen/additive registries; no existing type number is reinterpreted. **No new domain label is needed** for the sheet checksum or snapshot AEAD; their frozen context expressly covers this use. If the specialist decides second-code confirmation needs an additional KDF or mixing step, they must approve and register a *new* label before implementation, not improvise it in code.

## Metadata/privacy analysis

The second sheet repeats the existing Home host, port and recovery scope in physically held code; copying or photographing **either** sheet exposes locator linkage. The second key never passes to a Home and supplies no new API field, request or write timing. The Home already knows record location, size bucket, writes and refreshes; key 8 must be inside the outer padded AEAD, so the Home cannot distinguish key-7 vs key-8 plaintext. The holder of the root alone still learns that a relationship snapshot *exists only through its authenticated record and resulting failure to open key 8*; not the contacts themselves. A person who loses the second sheet gives up contact restore. Old records, old controller kits, backups made under old profiles and a compromised endpoint remain residual risks; this is **not retroactive secrecy**. Require a UI that does not expose the relationship code in confirmation logs, autofill, screenshots or copy history.

## Independent vectors required before enablement

- `RK2-01`: key = 32 bytes `00..1f`, scope = 32 bytes `a0..bf`, `port=0`, host `home.example`, checkpoint for AccountID=`11*32`, generation=7, digest=`22*32`: **v2 kind `03`**, exact length **85+length(canonical checkpoint)** bytes, fixed binary/Base32/line-check/QR golden encodings and round-trip; reject kind `01/02`, wrong scope, malformed/punycode host, checksum flip, trailing byte, v0 and legacy-35 input. Supply *byte-for-byte* golden values from a Python and a Rust encoder (do not use a shared encoder as oracle).
- `RK2-02`: root = 32 bytes `40..5f`, relationship key = `00..1f`; assert no derivation/wrapping, unequal and scope-bound input. Exhaustively test syntactically valid wrong-kind submissions never enter a cipher.
- `RK2-03`: fixed canonical `relationship-snapshot`, scope `a0..bf`, generation 0x1234, 12-byte nonce `00..0b`, key `00..1f`: golden CBOR, AAD, AES-256-GCM-SIV ciphertext+tag, and negative wrong key/generation/scope; reject duplicate keys 7+8.
- `RK2-04`: 1 anchor + 1 segment + 8 tail + 1 head, valid successor chain; mutate an anchor hash, missing interior state, duplicate state, extra/missing credential, epoch or recovery link. Need distinct `needs_evidence` vs `saved_sheet_older_than_recovery`; with >65 states returns `needs_new_safety_code`. Restart and scope/locator floor migration cases.

## Gate and authority

This is an accepted, gated specification, **not permission to turn it on**. Before any code ships or is enabled: the normative additive revision of [`recovery-sheet.md`](../spec/protocol/recovery-sheet.md) (which today documents version 1 only; the version 2 text of ADR-0203 section 1 is owed there as well), the CDDL and the numeric-field registry rows are written together with vectors `RK2-01` to `RK2-04` from two independent codecs (a Python and a Rust encoder, neither used as the other's oracle), and a cryptography/protocol specialist approves the key custody, the sheet amendment and the restore-state distinctions. A change to audited text that the specialist finds necessary goes to the operator as a question, not into code. The RecoveryRoot continues to confer only its previously audited recovery powers.

## Import notes (collision check and edits, 2026-11-19)

- **Values checked, no collision.** Sheet version `0x02` kind `0x03`: version 2 allocates only kind `0x01` (ADR-0203 section 1) and version 1 allocates `0x01` and `0x02`, so `0x03` is free. `RecoveryKit` key 11: the kit uses keys 0 to 10 and 23. `recovery-acs-evidence` key 4: the struct uses keys 0 to 3. `RecoveryRecord` keys 7 and 8 already exist (ADR-0199 section 3). No new domain-separation label is introduced; the checksum label `OM-RECOVERY-SHEET-CHECK-v1`, the snapshot AAD label `OM-RECOVERY-RELATIONSHIP-SNAPSHOT-AEAD-AD-v1` and the key label are already registered.
- **Reserved, not registered.** Following the precedent of ADR-0225 to ADR-0229 (documents only), no CDDL, registry or sheet specification file is changed by this ADR. The values above are reserved by this ADR text until the gate opens.
- **Relation to ADR-0225.** Sections 1 to 7 give the byte-level form of what ADR-0225 sections 1 to 4 decide in outline (the second written code with a distinct kind value, the anchor and its segment, the restore states, the floors). Where the two read differently, ADR-0225 wins and this ADR is corrected. The rule that a Maximum Privacy account with only the interim empty snapshot is never reported as fully "On" is an additional fail-closed status rule.
