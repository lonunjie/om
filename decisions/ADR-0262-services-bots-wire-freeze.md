# ADR-0262 — W4 `services_bots` canonical wire freeze

- **Status:** Delegated design decision — repo-local W4 wire freeze; **independent review remains required**.
- **Date:** 2026-11-23
- **Scope:** W4 `services_bots` wire forms and the reserved `ConversationEvent` representation key 13; no W0, W1, W2 or W3 receiver change.
- **Precondition:** ADR-0258 authorizes engineering of `services_bots` under a pre-engineering waiver; the V-011 pre-release obligations and ADR-0156 independent-codec/review criteria remain open. This ADR does **not** authorize release.
- **Authority:** This is a **delegated design decision**, not an operator's separate approval, not an amendment to audited design text, and not independent review.

## Decision

Freeze the W4 forms in [`spec/cddl/service.cddl`](../spec/cddl/service.cddl) and add assignments to the existing, otherwise unchanged registries:

| Object | Type | Envelope / roles | Body hash | Max encoded bytes |
| --- | ---: | --- | --- | ---: |
| `ServicePrincipal` | 47 | None (public identity-reference wrapper) | None; **ServiceID remains a random stable 32-byte ID** | 256 |
| `ServiceControlState` | 48 | `SignedEnvelope`, `controller` (role 1) | `OM-SERVICE-CONTROL-HASH-v1` | 65,536 |
| `ServiceDefinition` | 49 | `SignedEnvelope`, `controller` (role 1) | `OM-SERVICE-DEFINITION-HASH-v1` | 65,536 |
| `ServiceInstallation` | 50 | `SignedEnvelope`, `device` (role 3) for personal scope, `controller` (role 1) for Room/Space governance | `OM-SERVICE-INSTALLATION-HASH-v1` | 32,768 |
| `RepresentationGrant` | 51 | `SignedEnvelope`, `controller` (role 1) to issue/expand, `device` (role 3) **only to revoke** | `OM-REPRESENTATION-GRANT-HASH-v1` | 32,768 |
| `ContextDisclosureBundle` | 52 | No new signature; authenticated one-shot OM 1:1 session | `OM-CONTEXT-DISCLOSURE-HASH-v1` (receipt/dedup reference only) | 65,536 |

The signature labels are respectively `OM-SERVICE-CONTROL-SIG-v1`, `OM-SERVICE-DEFINITION-SIG-v1`, `OM-SERVICE-INSTALLATION-SIG-v1` and `OM-REPRESENTATION-GRANT-SIG-v1`. All nine new hash/signature labels are registered with use, construction, W4 wave, object and purpose. Hashes use the existing `DS-HASH` construction over the **body**; signatures use existing `DS-SIG` over canonical body bytes and the registered role. No new crypto primitive or role number is introduced.

`ConversationEvent` remains object type **10**. Its existing reserved numeric key **13** is now assigned only for W4 to `ServiceEventRepresentation` `{0: represented_account_id bstr32, 1: representation_grant_ref Digest}`. The canonical event continues to carry key 5 `author_principal` = `{0: 2, 1: ServiceID}` and key 6 `author_endpoint_id` = the authorized service endpoint credential. Key 13 never changes the cryptographic author to the represented account. A service not representing anyone may omit key 13. The payload under key 11 continues to satisfy the already-frozen corresponding event-kind schema, including an ordinary W0-valid `message.create`; streaming partials are **never** ConversationEvents. **No new event-kind number is required or allocated.** Existing key 14 (`foreign_provenance`) remains reserved to bridges.

**W0 behavior is unchanged and mandatory:** any W0 receiver encountering key 13 **rejects** the event as an unknown critical field. A W4 decoder must not turn a W0 rejection into an acceptance, a silent key drop, or an Account-authored fallback. This preserves ADR-0128 rule 18 and the W0 event schema.

## Important normalization

1. The logical schema's `authorization_evidence` on `ServiceControlState`, `issued_by_account_authority` on `RepresentationGrant`, and control/approval signatures are the existing `SignedEnvelope.signatures`, not duplicated inline signable blobs. `ServiceInstallation.approval_evidence` is a **digest reference to an external actual governance decision**, not an assertion of permission by itself.
2. `ServicePrincipal` is an unsigned wire wrapper for the public ServiceID, not a new source of authority or a hash-derived ID. Services, hosts and endpoints are never human AccountPrincipal devices.
3. Controllers are sorted, unique `ServiceController` records, with `kind = account / organization / Space / Room governance`. The service, an endpoint, a host or a Room role deriving from that service is **not** an eligible independent controller. Governance proof and controller-to-device key mapping are external authorization checks and must be verified; an envelope role label alone is not sufficient.
4. An endpoint credential has its own stable incarnation ID, status, crypto profile, public key, execution mode, and optional non-authoritative host ref. Migrating a host is an atomic authorized control transition and does not rotate ServiceID or transfer ownership.
5. Installation scope (`personal`, `Room`, `Space`) and read authority remain separate. Remote conversation access has only two cryptographic positions: `selected_context` invocation-only or explicit `full_room_member`. `local_personal` is device-local. A trigger filter merely limits wakeups; **it cannot restrict a full member's plaintext access**. A Space installation never grants child-Room content. Full membership requires the recorded ServiceControlState head and separately authorized MLS/Room admission.
6. A grant carries the issuing **control device ID** and exact AccountControlState version+hash basis; a messaging-only device may revoke, not issue or expand. The grant dies when its basis becomes invalid; notices to other account devices and any affected counterparty, actual counterparty consent, and recipient-set change are **mandatory external checks**. The notice reference field does not replace a displayed notice or permission to encrypt to a service.
7. A disclosure bundle is scoped to a single invocation, explicitly selected items, a purpose, an expiry, and optionally minimal scope/participant hints. It is delivered over a user-initiated authenticated OM 1:1 relationship and must produce a receipt. It is never a standing forwarder or a Room subscription. Bytes/manifest declarations have no power to grant tools or network egress.

## Canonical validation rules

- Apply OM-CBOR-v1: RFC 8949 shortest-form definite lengths, numeric map keys for typed structs, no CBOR tags, floats, negative integers, duplicate keys, indefinite lengths, invalid UTF-8 or trailing data. Enforce `max_bytes` **before decoding**. All explicit field and collection bounds are hard limits.
- In every typed map, reject unknown/reserved numeric fields and absent required fields; optional unused fields are **absent**, never CBOR null. Key 23 remains the existing extension mechanism: unknown noncritical extensions are ignorable, but unknown critical extensions and `om.critical.*` reject. No new extension identifiers are allocated here.
- Every registered `set` is sorted **bytewise by each element's full OM-CBOR encoding** and unique. Do not sort human text under Unicode collation or auto-fix a received set. Arrays that are not sets retain their semantic order (selected disclosure items).
- For a `ServiceControlState` chain, `state_version=1` has **no** `previous_state_hash`, every subsequent version has exactly one. Validate the prior state hash under `OM-SERVICE-CONTROL-HASH-v1`, strict progression against the greatest previously authenticated head, predecessor-controller threshold, signer eligibility and no-self-bootstrap. Reject stale or same-version-forked states. A revocation is a monotone reduction and is not held hostage by an unrelated fork: rebase it atomically on the accepted head, deliver the new head and revoke/Remove the endpoint in all installed Rooms under ADR-0129/ADR-0128. No revoked endpoint credential is reactivated.
- `ServiceDefinition` version and signature provenance are bound to the same ServiceID. Definitions **declare**, never grant, categories, commands, parameter-schema bytes, modes and desired capabilities. Unknown command schema bytes must fail closed for execution.
- Installation/grant update and revocation records use incarnation-preserving `version` + predecessor hash. On reception require the known predecessor, reject rollback, forks and revoked-to-active resurrection. Never make revocation dependent on increasing other powers, and never recreate revoked endpoint credentials on restart.
- On `ServiceInstallation`, enforce `full_room_member` only for Room scope and only with `state_head`; `local_personal` only for personal scope. A personal installation is device-signed; Room/Space governance installations are controller-signed and still require actual external governance authorization. Neither a service nor its installation-derived authority can approve itself. Approval, scope and Room/MLS membership remain independently required.
- For a new or expanded `RepresentationGrant`, require an active, non-quarantined **control device** signature matched to its named issuer, against its exact validated AccountControlState head. A messaging-only device signature is valid only for revocation. The represented service can never issue itself Account control, recovery, enrollment, key export or ungranted redelegation. A representation on an event must match the **active** grant hash, AccountID, ServiceID, scope, action, times, live control-device basis, permitted recipients and visible counterparty notice. Receiver needs authoritative known state for those external checks.
- Validate `author_endpoint_id` against current ServiceControlState and the installation/recipient relationship; `author_principal` stays a ServicePrincipal on every autonomous event. There is no service-originated Account send and no implicit bot-to-bot trigger. No new primitive bypasses event-kind guards or W0 capability negotiation.
- A triggering message counts as disclosed plaintext. A plaintext-tainted invocation cannot perform network egress without the conversation's **explicit `plaintext_egress` policy**, both participants' policy in a 1:1, or the strictly one-shot user-initiated exception. Tool execution is a capability-broker decision, not text parsing; enforce hop, per-root and per-invocation budgets. Reject rather than silently broaden a denied grant.

## Evidence

- The CDDL, complete object/field/domain-separation registries, and `verification/prototypes/services-wire/` provide **repo-local** evidence: one separately written Python 3 standard-library canonical CBOR encoder/decoder + schema/semantic validator, 21 positive and 80 negative exact-byte vectors, and a replay/round-trip runner. Vectors cover wrong signer roles, missing/unknown fields, range errors, noncanonical encodings, W0 key-13 rejection, stale/forked chains, revocation and absence/null rules.
- **No independent second codec** is included in this scope's requested artifact list. The vectors use structurally shaped test signatures; they do **not** verify real cryptographic signatures, independent governance proofs, MLS head propagation, recipient consent, tool-broker runtime behavior, or real-transport selected-context disclosure.
- Consequently this does **not** close V-011's independent-review or two-codec requirements and does **not** lift ADR-0258's release flag. Implementation replay, separate independent codec agreement, full V-011 models/corpus review, independent reviewer sign-off and release evidence are **still required**.

## Non-goals

No changes to W0 event kinds/receiver behavior; no W1 group event body schema, W2 call wire, W3 Space/Publication wire, or W4 bridge key 14; no ServiceControlHead **carriage transport** beyond the `state_head` reference; no new AccountID, centralized service issuer, discovery directory, bot platform, network egress permission, crypto primitive, automatic Account-authored bot send, arbitrary subscriptions, MLS membership transition, endpoint host protocol or plugin package format. No claim of release readiness or safety from an unaudited manifest.

## Choices where the design is silent

1. **ServicePrincipal wrapper:** type 47 is unsigned/unhashed with precisely the random ServiceID, because the architectural `PrincipalRef` is already the identity and no second identity key is authorized.
2. **Numerics and caps:** types 47–52; object maximum sizes in the table; 32-byte governance IDs and 16–32-byte incarnations; `1..2^32-1` state/update versions; 1–32 independent controllers and threshold; 0–128 separately revocable endpoints; all declared limits in CDDL/registry are deliberate bounds, not audited constants.
3. **Governance reference:** a controller has type 1 Account, 2 Organization, 3 Space or 4 Room plus 32-byte ID; this *does not* define governance verification, which must be performed by its existing policy. No host/service variant is assignable.
4. **Envelope roles:** controller for service control and definition; account device for personal installation, governance controller for Room/Space installation; controller to issue/expand representation and device only to revoke it. No new signature-role enumeration value.
5. **No extra inline signature:** the existing envelope carries service-control and grant authority evidence; approval decisions and notices use digest references requiring independent retrieval and validation.
6. **Stable chain incarnation:** installations and grants have explicit update versions and predecessor hashes, absent only at genesis. This prevents an old active record being mistaken for a later revocation. Definition releases have versions but **no invented cryptographic predecessor**, so same-version conflicts and stale versions are rejected using externally retained authenticated definition heads.
7. **Execution/data modes:** numeric enumerations 1–3 with the strict scope checks above; no `scoped_subscription` mode. Command schema is opaque, bounded bytes (`0..4096`) and may be executed only if a client supports its declared grammar; no unregistered arbitrary map parser hook.
8. **Automation:** bounded optional declarative rule entries and trigger filters; exact caps `max_hops=1..16`, actions per root `1..1000` are ceilings, not permission to run or acceptable default rates.
9. **Representation constraints:** optional bounded count, counterparty allowlist and per-action-confirmation flag; no generic arbitrary authorization map. A grant requiring another person's plaintext uses the exact `message.read_other_participant` action plus mandatory notice evidence reference, but **actual notice and consent must also be proven independently**.
10. **Disclosure item encoding:** kind 1 selected message, 2 attachment, 3 draft, 4 topic/thread, 5 explicit text; bounded opaque byte payload preserves the selected data, does not serialize an ambient roster or grant implicit metadata access. No `source_scope_hint` is emitted by default. Unsigned bundle integrity comes from an authenticated one-shot session; its hash label is only for receipts/deduplication.
11. **Represented event key:** event key 13 is a two-field map of represented AccountID and immutable grant digest; no new event kind, no event signature, and no Account-authorship rewrite. Unsupported W1 group-event bodies are not newly frozen or accepted merely because this overlay exists.
12. **Availability/expiry:** absolute Unix-seconds hints are explicit integer fields; clock skew, receipt delivery, accepted prior head, endpoint authorization and cross-party policy are authenticated *external state*, not implied by a canonical CBOR parse.

All these choices are constructions under delegation, not amendments to audited consent, floor, authority or W0 rules. Independent review remains required.
