# ADR-0184 — Chat-history backup file (`OMB-1`): a password-sealed, history-only file; restoring grants no authority

## Context

The 2026-11-03 capacity report found Core had no history export and that a SeedLife-operated backup store would make the project a custodian of everyone's encrypted history, which conflicts with "operatorless" ("Where did authority go?": to us). Its recommended order was (1) an archive in Core, (2) a file the person saves wherever they like, (3) optional destinations the person connects. The operator approved (1) and (2).

The existing design already says what a history archive is and is not (IMPORT_EXPORT sections 7 to 10), but no archive-encryption profile is frozen: `OMA-ENC-1-candidate` is "verification-only, not an allowed production profile" (ADR-0125 rule 5, ADR-0139), and the full OM Portable Archive (container, manifest, blobs, provenance classes) is the locked `portability` scope. Waiting for V-014 would mean no backup for a long time. This ADR therefore defines a **much smaller object** that stays inside the rules the design already gives, and does not pretend to be the Portable Archive.

## Decision

1. **A new, separately typed object: the chat-history backup file, format `OMB-1`.** It is not an OM Portable Archive, never claims to be one, and does not reuse the name or constructions of `OMA-ENC-1-candidate`. It carries conversations and messages for one profile and nothing else. Layout, key schedule and limits are normative in [`backup.rs`](../crates/om-core/src/backup.rs) (module documentation) and mirrored in the report.
2. **Encryption profile `OMB-ENC-1`** (id 1 in the file header): Argon2id (RFC 9106) over the password, run by the host; HKDF-SHA-256 (RFC 5869) from the Argon2id output with the file salt as extract salt and the labels `OM-BACKUP-v1 aead key` and `OM-BACKUP-v1 key check`; XChaCha20-Poly1305 over the whole body with the 84-byte header as associated data and a fresh random 24-byte nonce. A fresh random 16-byte salt is drawn from Core's CSPRNG per file. Nothing is invented: every primitive is standard and already in the workspace or in the vault (`@noble/hashes` Argon2id, the same cost the vault's passphrase layer uses: 64 MiB, 3 passes, 1 lane). The password is NFKC-normalised like the vault's. No new dependency.
3. **Cost bounds are checked before any key work, in both directions.** Floor 65,536 KiB and 3 passes (the candidate's floor), ceiling 262,144 KiB, 10 passes, 4 lanes (what a browser can hold). A file outside them is `unsupported_parameters`. Only a build with the insecure test RNG (which cannot be combined with `production`, R-072) writes and accepts token costs, so tests and vectors stay fast without a switch in the shipped artifact.
4. **Typed refusals, all-or-nothing.** `not_a_backup`, `unsupported_version`, `unsupported_profile`, `unsupported_parameters`, `truncated`, `malformed`, `wrong_password`, `tampered`, `invalid_content`, `too_large`. A 16-byte key check (HKDF output, independent of the header) tells a wrong password from damage: changing the salt or cost makes the key differ and reads as `wrong_password` (unavoidable); changing the nonce, the ciphertext length or any ciphertext byte with the right password is `tampered` or a length error. A read returns the whole body or an error; the import is one staged transaction committed before release, so a refusal, a failed commit or a limit breach leaves the profile exactly as it was.
5. **The body is built from an allow-list** (`backup::collect`): per conversation its id, the other person's display name, the other person's public AccountID and ConversationID as hints, the creation time, and per message its id, direction, text, time, a coarse delivery state, the event clock and the SHA-256 of the canonical event (kept as evidence, not proof). It never contains account, recovery, device, MLS, session, delivery, request or intro keys or seeds, mailboxes, routes, relay entries, the outbox, replay records, credentials or control-state chains. A field added to the profile state later is **not** exported unless this list is changed. Deleted messages are not exported. ViewOnce and expiring content do not exist in Core yet; when they do, ADR-0129 applies and this list must exclude ViewOnce and carry expiry.
6. **What a restored profile can do (the conservative reading, normative).** Importing creates **restored conversations**: read-only history stored beside, never inside, the profile's relationships. A restored conversation has no relationship, key, mailbox, route or outbox entry. It can be listed, read, and included in a later backup. It cannot send, retry, receive, be polled, be blocked as a person, or change any governance or control state. The restored profile has its own account and device identity (a fresh install creates its own); importing never touches them. A conversation that is already live on this device is left alone (its messages are not replaced). Restored messages are marked as an unverified copy: the file is unsigned, so it proves integrity to someone who knows the password and proves nothing about who wrote the messages (ADR-0125 rule 5). To talk to a person again after losing a device, the two start again from an invitation.
7. **Limits.** At most 6 MiB per file (the host bridge carries bytes as hex in one 16 MiB command), 10,000 conversations, 250,000 messages, 64 KiB per message text. Core refuses to write more (`too_large`); an importer refuses more.
8. **Core does not see the password.** The host derives the 32-byte key and gives it to Core, which uses it for one call and zeroizes its copy. (The JSON bridge carries the key as hex, so a copy exists in host memory until collected; this is the same exposure the vault's passphrase path has and is recorded as residual risk.)
9. **Registry.** The two HKDF labels are registered in [`om-domain-separation.json`](../spec/registries/om-domain-separation.json) (use `kdf_info`, wave `W1`, status `frozen`).

## Where did authority go?

Nowhere new. The person holds the file and the password; SeedLife holds nothing and is not in the path. The file cannot send as the account (it holds no key), cannot change governance (it holds no control state), and restoring it cannot resurrect a relationship (restored chats have none). Whoever holds the file and password can read the history, exactly as whoever holds an unlocked device can.

## Consequences

- A person can leave a lost device behind and keep their history on any storage they choose, with zero infrastructure of ours. Identity continuity after device loss is still the recovery/device-linking design (multi-device plan phases 1 and 4), not this file.
- The Portable Archive, human-readable export, attachments, selective export and foreign imports remain locked (`portability`); `OMB-1` deliberately does not become their base. If the Portable Archive is later authorised, a reader for `OMB-1` can be kept as a legacy importer; the version byte allows it.
- User-connected destinations (a person's own bucket or drive) are step 3 of the capacity report and out of scope here. They would only move the same sealed file.

## Verification

Rust: format vector ([`verification/vectors/om-backup-file-vectors.json`](../verification/vectors/om-backup-file-vectors.json)), every-byte-flip and every-truncation tests, typed-error table, cost floor/ceiling, secrets-absence scan over the whole profile state, no partial import (hostile body, failed commit), idempotent and incremental restores, restart persistence, bridge commands. TypeScript: pinned Argon2id vector, NFKC equivalence, services, screen (axe), real-Core round trip. Playwright (Chromium, Firefox, WebKit): two people talk, one saves a file, a fresh browser restores it, reads the history, has no composer, and wrong password, changed file, cut file and non-backup are each refused and import nothing.
