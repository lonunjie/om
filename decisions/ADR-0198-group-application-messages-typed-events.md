## Context

Group messages travelled as a Core stand-in: MLS application plaintext `{"k":"text","id":...,"text":...}` (JSON). No audited text fixes that plaintext. The documents that do speak of what a Room carries speak of `ConversationEvent`s (EVENT_MODEL; ADR-0176 extends the dispatch by an overlay for the W1 kinds; GROUP_CHAT_ARCHITECTURE section on live deduplication). The one-to-one chat already carries reply (`message.create` key 2), reactions (`reaction.set`, kind 4), edit (kind 2) and delete (kind 3) on exactly those frozen bodies (D140 to D142). A Room had no way to say any of them (question Q-CHAT-1), so a group lacked four everyday gestures.

## Decision

1. **The application message of a Room is a canonical `ConversationEvent` (object type 10, W0 rules of [`events.cddl`](../spec/cddl/events.cddl), kinds 1 to 4).** The MLS application plaintext is the event's canonical bytes, built by the same `events::Header` the one-to-one chat uses. `conversation_id` is the Room's ConversationID, `author_account` and `author_device` are the sender's, the clock is an HLC the sender keeps per Room (strictly increasing, never behind the wall clock), and `event_id` is 16 random bytes. A message's id is that EventID (hex), as it already was for the JSON text.
2. **Discriminator and the older payload.** A CBOR map never starts with the byte `{` (0x7B), so the first byte tells the two apart with no new tag: a payload starting with `{` is the older JSON text and is read exactly as before (an older message still renders, can be replied to, reacted to and edited by its author; its text register is ordered before any edit); anything else is a typed event. A payload that is neither valid JSON text nor a W0-valid `ConversationEvent` is dropped (`unsupported_event`), except that a payload starting with `{` that is not a text message is still refused as `malformed_event`, as before.
3. **Sender authentication comes from MLS, never from the event.** The receiver takes the sending device and epoch from MLS and the account from its own Room directory. It accepts a typed event only if `conversation_id`, `author_account` and `author_device` equal the Room, that account and that device (else dropped, `event_author_mismatch`). The event's own claims are never authority.
4. **Authorization per kind, at the sending epoch** (ADR-0121 rule 7; this engine keeps no older epoch window, so the head stands for it, as for every group message before): a message needs `room.post`, or `room.reply` when `reply_to` is set; a reaction needs `room.react`; an edit needs what the original post needed; a delete of one's own message needs authorship only. Only the author may edit or delete (another member's edit or delete is dropped, `not_author`; moderation stays `moderation.redact`). A reaction is a register per (member account, message, key). A removed or departed member is not in the Room directory, so anything of theirs after the removing Commit is dropped or refused by the engine before it is read.
5. **Order.** Edits and reactions are epoch-major last-writer-wins registers ordered by `(sending epoch, EventClock)` (ADR-0121 rule 3), the epoch being the one MLS authenticated. A register takes an event only if ordered after what it holds, so replay, reorder and repetition converge. A delete is final (the record stays with its text and reactions cleared, so a late edit or replay cannot bring it back). A message create with a known id is not applied twice.
6. **Fail closed on the unknown.** A kind other than 1 to 4, a create with attachments, mentions, expiry, thread or topic (keys 1 to 6 beyond text and `reply_to`), a body that does not parse, or a reply to itself is dropped with a reason and changes nothing; it never fails the receive and never half-applies. A target that is not in the Room (not arrived, deleted, never seen) is accepted with no effect, as D141 and D142 do for a one-to-one chat; ADR-0121 rule 6 would buffer it (`dangling`): that is a departure, recorded as D143.
7. **Bounds.** Text is at most 8192 bytes (the bound a group text has always had); a reaction key is 1 to 64 bytes with no control character; at most 16 reaction registers per member and message (a removed one makes room).
8. **What does not change.** `GroupTransportFrame` kind 3 `app` still carries one MLS application ciphertext; no frame field, relay-visible byte, object type, MLS extension, CDDL or registry entry changes. The stored Room message record gains optional fields that default when absent, so an older stored record loads. A build older than this ADR refuses a typed payload (`malformed_event`, nothing applied or shown). Groups have not shipped to users (ADR-0177 item 2 keeps public release blocked), so no deployed build needs to read the new form; the older JSON text stays readable by this one.

## Where did authority go?

Nowhere new. Who may speak, react, edit or delete is decided by the Room's own capabilities (ADR-0121 rule 7) and authorship; who sent a message is what MLS and the Room directory say. No service, relay or Home learns anything it did not (it sees one sealed frame, as before).

## Evidence and what is not covered

- Core tests in both feature modes (fake engine and OpenMLS) over a three-account room: reply, reactions per member, edit, delete, author-only enforcement, spoofed author, removed member's late reaction, unknown kind, malformed payload, older JSON text, replay and reorder. The real wasm module runs the same through the groups binding test. A Chromium run of three people covers the screens.
- No new vector: the bodies are the frozen W0 kinds 1 to 4 and every event written or accepted here is checked against the W0 `ConversationEvent` registry rule. A two-codec vector for events inside an MLS application message is not written; the carriage is OM-level plaintext inside MLS, not a frozen wire object.
- Not built: buffering of a state event whose target has not arrived (ADR-0121 rule 6), equivocation handling for two payloads with one EventID (the first is kept, ADR-0121 rule 5), the past-epoch window (the engine keeps none), expiry (`disappearing_timer` is not applied to these events), attachments, mentions and threads in a Room.
