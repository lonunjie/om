# ADR-0254 — Expressive-media pack distribution: one portable file, carried as an ordinary attachment (slice 6)

- **Status:** Accepted by delegation (2026-11-20), additive. No wire change and no change to the frozen W0 or W1 corpora. It amends no audited text and weakens no cryptographic floor. Fail-closed: a source the design gives no safe route for is left out.
- **Date:** 2026-11-20
- **Scope:** engineering scope `expressive_media` (ADR-0250), build-plan slice 6, the "distribution decision" that the slice-6 report found missing.
- **Class:** Engineering and product boundaries. Companion of ADR-0252 and ADR-0253.

## Context

The build plan names three install sources (a received message, a portable file, a link or QR) but defines no interoperable payload. ADR-0252 rule 9 forbids locations and repair capabilities inside a release; rule 7 limits the on-message `pack_ref` to claimed attribution. Constitution rules C-06, C-63, C-65 and C-81 forbid a default catalog, a compiled-in fetch address or a mandatory project service, and the privacy-profile rule forbids automatic third-party fetching.

## Rulings

1. **One portable container.** A pack travels as a **pack file**: media type `application/vnd.om.content-pack`, extension `.ompack`, a canonical CBOR map (the existing `om-codec` canonical rules) with: key 1 the text `om.content-pack-file.v1`; key 2 the canonical `ContentPackRelease` bytes (object type 45); key 3 an ordered array of canonical `ContentPackControlState` bytes (object type 46) forming the chain the release needs; key 4 an array of `{digest, bytes}` entries, one per release item asset. The file is a local interchange format, not a protocol object: it is never signed as a whole, adds no registry value and no critical field, and its authority is exactly that of the contained release and control states (verified by Core, slice 3). Unknown top-level keys are rejected.
2. **Strict validation before any install step.** Reject, with a stable reason and nothing staged: wrong format text, non-canonical encoding, a release or control state that fails slice-3 verification, more than 64 control states, more than the release's own item count of blobs, a missing blob, a duplicate digest, a blob no item names, a blob whose digest or header facts fail the `om.expressive.budget-v1` walker, and an aggregate size above the release's declared size plus 64 KiB of container overhead and never above 32 MiB. Install is staged then activated atomically by Core (slice 3); a failure at any write leaves the prior install active.
3. **Received OM message: an ordinary attachment.** Sharing a pack sends the pack file as a normal attachment with that media type under the existing attachment limits and blob handling. No pack semantics are added to `message.create`, no new extension, no new object type. A recipient's client recognises the media type and offers **Review pack**, which is the same flow as importing a file (ADR-0253 ruling 4: explicit confirmation naming the pack). A pack larger than the ordinary attachment limit cannot be sent this way; that is accepted for W1. The sender's identity is shown as who sent the file, never as a trust statement about the pack (R-108).
4. **Portable file import.** The person picks or drops a `.ompack`; same validation and review flow. Nothing is read from the network.
5. **Link and QR: not built in W1.** The design defines no resolver for a pack link: resolving a release identifier needs a catalog or a web origin, which C-06, C-63 and C-81 forbid as a default and the privacy-profile rule forbids as an automatic fetch. Building one would invent a service. No pack link, QR or deep-link route ships; a person receives a pack file by message or by file. Consequently no acquisition network path exists in any privacy profile, and the Maximum Privacy rule is satisfied structurally (and asserted by a request-log test). Recorded for the operator as a possible later ADR with its own resolver design.
6. **Profile-local cache.** Installed item ciphertext is stored under the profile's blob store keyed by digest; previews are produced only by the slice-4 decoder after Core validation. The one-shot wasm install command's 16 MiB JSON limit is not a design limit: install uses a staged begin, stage-one-blob, commit sequence so a valid full pack fits. Removing a pack never alters a received message (C-04).
7. **Inline emoji projection.** The timeline projection is not changed in W1. Inline custom emoji render only where an authenticated semantic placement is available; elsewhere the ordinary fallback text shows, which is the W0-valid behaviour (ADR-0155). Changing the stored projection to retain placement with the winning revision is deferred; recorded for the operator.

## Consequences

Slice 6 builds the container codec and its hostile corpus, the staged install in Core, the cache reader and the import and message-attachment recognition in the UI; a pack-file golden-vector set is added so a second implementation can interoperate, but the container is not frozen as protocol. Any link, QR or catalog route, or a change to rulings 1 to 3, needs a new ADR.
