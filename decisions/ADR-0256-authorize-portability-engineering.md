# ADR-0256 — Authorize engineering scope `portability` (W1), by explicit operator instruction

- **Status:** **Accepted** (operator, 2026-11-23, explicit instruction in chat; not delegation). Authorizing an engineering scope is a decision of the operator, not a review result and not a delegation. The operator's instruction was conditional: authorize each remaining scope that is part of the design and aligns with the constitution. This ADR records that check for this scope.
- **Date:** 2026-11-23
- **Authorizes:** engineering scope `portability` only. No other scope changes state through this ADR.
- **Depends on:** the scopes named in `depends_on` for `portability` in the repository contract, already authorized.
- **Waives:** the **pre-engineering** phase of gate V-014 for engineering purposes only. Its pre-release phase is untouched and stays open.

## Context

`portability` (W1) is part of the complete, audited design and its scope contract exists in [`engineering_scope_contracts.json`](../machine/engineering_scope_contracts.json). Constitution check: C-12 and C-17: identity, history and relationships belong to users and survive any dependency; export is the user's own escape path, with no new authority. The design queue has no open blocking item for it. The unlock contract ([`RELEASE_WAVES_AND_SCOPED_ENGINEERING_UNLOCK.md`](../docs/process/RELEASE_WAVES_AND_SCOPED_ENGINEERING_UNLOCK.md) section 5) otherwise requires every gate that lists the scope to have `pre_engineering_status` passed or waived by an ADR. Gate V-014 still has criteria open: the frozen `om-archive-v1` specification and vectors (the hostile corpus and the reference reader/writer prototype are met), and independent review of the archive-encryption profile that the scope contract names as an integration prerequisite. The operator may choose to authorize engineering now and keep that evidence as a release obligation. This is the same shape as ADR-0250, ADR-0217 and ADR-0183.

## Decision

1. **`portability` is authorized**, by explicit operator instruction. Engineers follow [`ENGINEER_START_HERE.md`](../docs/process/ENGINEER_START_HERE.md), the `portability` entry of [`engineering_scope_contracts.json`](../machine/engineering_scope_contracts.json) and the design gate in [`AGENTS.md`](../AGENTS.md).
2. **What the scope covers.** `om-archive-v1` export and import: staged, resumable export and import of a person's own canonical objects, unknown named extensions and stable event and object identities, restore that never overwrites newer live authority, security floors or provider capabilities, and the hostile-archive reader. Sources: [`IMPORT_EXPORT_AND_USER_ESCAPE.md`](../docs/architecture/ecosystem/IMPORT_EXPORT_AND_USER_ESCAPE.md), [`RECOVERY_AND_BACKUP_POLICY.md`](../docs/architecture/identity/RECOVERY_AND_BACKUP_POLICY.md).
   - **Not covered:** any archive-encryption profile shipped as production crypto (`OMA-ENC-1-candidate` stays a candidate), importers for foreign networks, and any hosted export or import service. Each needs its own ADR.
3. **Gate V-014 pre-engineering is waived by this ADR, for engineering only.**
   - *Risk accepted:* archive reader and writer code, and the archive wire, can be written before the specification is frozen with vectors and before the archive-encryption profile has had independent review; a construction chosen during engineering could be found wrong later, and a hostile archive could reach a reader whose corpus coverage is only the repo-local one.
   - *Compensating controls:* (a) the first build slice freezes this scope's wire objects (CDDL, registered numeric fields and domain-separation labels, positive and negative vectors, two independently written codecs agreeing) before any other product code, by the V-005 method, additively and under ADR-0165; (b) the feature is built behind a capability flag that is off in every release until the release evidence below is in, and no production build offers it; (c) every construction the design leaves open is written in an ADR by delegation that does not amend audited text, and where the design is silent the engineer writes the question in the scope's plan and stops; (d) no wire requirement is added to an earlier wave beyond the reserved extension and criticality points already frozen in V1 semantics (RELEASE_WAVES rule 1); (e) export may be built unencrypted-by-profile only as an explicit user-held-file path with no claim of confidentiality; no archive encryption profile is offered, advertised or defaulted until it has independent review, and `OMA-ENC-1-candidate` never ships as production crypto; (f) import is staged and never makes archived authority, routing or security state live; restore never overwrites newer live authority, floors or capabilities (scope contract forbidden shortcuts).
4. **Still required BEFORE RELEASE, not before engineering.** two independent implementations round-trip, real foreign importers pass authority and provenance tests, and the archive-encryption profile has independent review; any release offering archive export or import, declaring `portability`, or claiming interoperable export needs them. `om-open-beta-1` does not list `portability` and stays as it is. Authorization is not release: nothing here edits a public release declaration.
5. **Constraints.** No new cryptographic primitive and no weakened floor (C-20); no mandatory third-party service and no project-operated service for this scope (C-01); no design change. Where the design is silent the engineer writes the question in the scope's plan and stops, or an ADR by delegation records a construction that does not amend audited text. The first deliverable for the scope is a build plan that states which design documents were read.
6. **Where did authority go?** Nowhere new. An archive is the person's own copy of data they already hold; importing one grants no authority the live control state does not already grant.

## Consequences

- The review basis becomes the operator's decision, not independent review. The open independence criteria of V-014 move to the release obligations in point 4.
- The first slice is design-bound specification and test work (wire freeze and the evidence harness named above); no feature code is reachable in any build until the capability flag is turned on by a later, evidenced decision.
