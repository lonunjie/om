# ADR-0258 — Authorize engineering scope `services_bots` (W4), by explicit operator instruction

- **Status:** **Accepted** (operator, 2026-11-23, explicit instruction in chat; not delegation). Authorizing an engineering scope is a decision of the operator, not a review result and not a delegation. The operator's instruction was conditional: authorize each remaining scope that is part of the design and aligns with the constitution. This ADR records that check for this scope.
- **Date:** 2026-11-23
- **Authorizes:** engineering scope `services_bots` only. No other scope changes state through this ADR.
- **Depends on:** the scopes named in `depends_on` for `services_bots` in the repository contract, already authorized.
- **Waives:** the **pre-engineering** phase of gate V-011 for engineering purposes only. Its pre-release phase is untouched and stays open.

## Context

`services_bots` (W4) is part of the complete, audited design and its scope contract exists in [`engineering_scope_contracts.json`](../machine/engineering_scope_contracts.json). Constitution check: C-88 (interoperation with services, bots and LLM agents is a goal within explicit security boundaries and user consent), C-12 and C-18. The design queue has no open blocking item for it. The unlock contract ([`RELEASE_WAVES_AND_SCOPED_ENGINEERING_UNLOCK.md`](../docs/process/RELEASE_WAVES_AND_SCOPED_ENGINEERING_UNLOCK.md) section 5) otherwise requires every gate that lists the scope to have `pre_engineering_status` passed or waived by an ADR. Gate V-011 still has criteria open: the ADR-0156 wire freeze with two-codec vectors for `ServicePrincipal`, `ServiceControlState`, `RepresentationGrant` and `ConversationEvent` key 13, and independent reviewer evidence (the bounded models, the injection and capability-broker corpus and the incarnation checks are met). The operator may choose to authorize engineering now and keep that evidence as a release obligation. This is the same shape as ADR-0250, ADR-0217 and ADR-0183.

## Decision

1. **`services_bots` is authorized**, by explicit operator instruction. Engineers follow [`ENGINEER_START_HERE.md`](../docs/process/ENGINEER_START_HERE.md), the `services_bots` entry of [`engineering_scope_contracts.json`](../machine/engineering_scope_contracts.json) and the design gate in [`AGENTS.md`](../AGENTS.md).
2. **What the scope covers.** `ServicePrincipal`s, service installations and endpoints, `RepresentationGrant`, and LLM agents acting through granted capabilities, in the two positions the design names (invocation-only and full member). Sources: [`SERVICE_PRINCIPALS_BOTS_AGENTS_AND_LLMS.md`](../docs/architecture/ecosystem/SERVICE_PRINCIPALS_BOTS_AGENTS_AND_LLMS.md), [`SERVICE_CREATION_DISCOVERY_AND_DELEGATED_AGENCY.md`](../docs/architecture/ecosystem/SERVICE_CREATION_DISCOVERY_AND_DELEGATED_AGENCY.md).
   - **Not covered:** any project-hosted bot platform, bot catalog or LLM service (C-01), any service that masquerades as an account, any autonomous Account-authored sending. Each needs its own ADR.
3. **Gate V-011 pre-engineering is waived by this ADR, for engineering only.**
   - *Risk accepted:* service and agent code can be written before the wire is frozen and before independent review, so an authority or egress boundary could be found wrong after code exists, and an injected prompt could reach a capability path that has not had independent review.
   - *Compensating controls:* (a) the first build slice freezes this scope's wire objects (CDDL, registered numeric fields and domain-separation labels, positive and negative vectors, two independently written codecs agreeing) before any other product code, by the V-005 method, additively and under ADR-0165; (b) the feature is built behind a capability flag that is off in every release until the release evidence below is in, and no production build offers it; (c) every construction the design leaves open is written in an ADR by delegation that does not amend audited text, and where the design is silent the engineer writes the question in the scope's plan and stops; (d) no wire requirement is added to an earlier wave beyond the reserved extension and criticality points already frozen in V1 semantics (RELEASE_WAVES rule 1); (e) a service principal never masquerades as an `AccountPrincipal`; a plaintext-read capability never implies network egress or arbitrary Room authority; (f) a permission or egress denial is never retried under a broader capability, restart never widens grants or recreates revoked installation credentials, and external side effects of uncertain outcome stay pending until reconciled.
4. **Still required BEFORE RELEASE, not before engineering.** implementation tests replaying the model vectors and the injection corpus, plus the independent review; any release offering services, bots or agents, declaring `services_bots`, or claiming agent safety needs them. `om-open-beta-1` does not list `services_bots` and stays as it is. Authorization is not release: nothing here edits a public release declaration.
5. **Constraints.** No new cryptographic primitive and no weakened floor (C-20); no mandatory third-party service and no project-operated service for this scope (C-01); no design change. Where the design is silent the engineer writes the question in the scope's plan and stops, or an ADR by delegation records a construction that does not amend audited text. The first deliverable for the scope is a build plan that states which design documents were read.
6. **Where did authority go?** Granted only by explicit Room or account grants to a distinct ServicePrincipal; it is never an account and never inherits more than its grant.

## Consequences

- The review basis becomes the operator's decision, not independent review. The open independence criteria of V-011 move to the release obligations in point 4.
- The first slice is design-bound specification and test work (wire freeze and the evidence harness named above); no feature code is reachable in any build until the capability flag is turned on by a later, evidenced decision.
