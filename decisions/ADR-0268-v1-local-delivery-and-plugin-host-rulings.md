# ADR-0268 — v1 rulings for scoped-engine hosting, local-delivery revocation and probing, and plugin host budgets

- **Status:** Delegated design decision (additive; independent review remains required).
- **Date:** 2026-11-27
- **Scope:** `local_delivery`, `bridges`, `portability` and `plugins` host wiring, and the reference PWA plugin host.
- **Authority:** delegated by the operator on 2026-11-27 ("decide on the constitution, usability, ease-security balance and security levels"). It amends no audited text, lowers no floor and adds no authority path.

## Decisions

1. **Scoped engines stay in the engineering module for v1.** The commands and typed clients for local delivery (nearby choice, signalling), bridges, portability and plugins stay behind the `scope-engines` feature. No release host supplies the matching services, so the release artifact, its size budget and its audit surface are unchanged. Each scope moves into the main module only at its own release gate, with its gate evidence, by a new ADR. Why: releases keep these features off until evidence exists (V-024 real devices for local delivery, V-010 for plugins, V-013 for bridges), and moving them earlier would enlarge what every user must trust for a feature few will use at first.
2. **Peer-device revocation ends the pair seed.** When Core adopts a newer authenticated control head of a peer and that head revokes or quarantines any device that was active when the pair seed was established, Core destroys the pair seed (the same destruction as for a block). Local-delivery signalling for that pair then reports `no_seed` and stays unavailable until a new session establishes a new seed; delivery over the Home is unaffected. Why: a removed device may hold the seed, and the seed's only job is to gate unauthenticated local signalling, so losing it costs convenience, never delivery. The reference Core records a peer's control head only at binding today, so this rule has no trigger until head ingestion exists; it must be implemented together with that ingestion.
3. **The capability probe is policy-gated.** The local-delivery probe opens two loopback peers and gathers host candidates, which a browser may announce on the local network. It never runs under Hardened or Maximum Privacy (local rendezvous is off there, ADR-0130 rule 8), never at startup, and under other profiles only when the user opens the local-delivery setting. When policy forbids it the row reports `unavailable` with reason `off_by_policy` and no peer connection is built. The probe result still means only that this runtime can build the channel.
4. **Reference PWA plugin host budgets** (host configuration; the wire sets none, ADR-0266 rule 11). Reference defaults for the low-end class of the V-022 budgets: at most 4 plugin instances running at once; at most 16 MiB of Wasm linear memory per instance; at most 48 MiB across all instances (about a third of the 150 MB steady-state budget). An instance that would exceed a limit is refused at start with a named reason; a running instance is never evicted silently. A host may lower these, never raise them past what its own measurements support.
5. **Reaffirmed as not in v1** (rulings of 2026-11-26): a LAN `fetch_async_key` responder, invite-seeded signalling and offline first contact over LAN, and autonomous plugins. Each changes who may hand out key material or hold a credential and needs its own ADR, vectors and review; usability does not justify changing authority silently, and the Home path already covers each need.

## Consequences

The reference web host gains an engineering-only adapter layer over the scoped engines, not part of any release bundle. Plugin frames run only when the host-side limits above are configured. Release notes keep saying plainly what is not in v1.
