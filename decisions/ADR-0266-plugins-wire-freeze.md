# ADR-0266 — W4 `plugins` canonical wire freeze and initial capability-only `om:plugin` world

- **Status:** Delegated design construction — repository-local W4 wire/prototype **only**. No independent review; flag **off**.
- **Date:** 2026-11-24.
- **Scope:** nine plugin object types 59–67, their W4-only fields/enums/labels, CDDL and canonical test corpus, and the first `om:plugin` WIT world. No edits to W0–W3 wire or W4 service/bridge assignments.
- **Authority:** ADR-0259 authorized engineering, waived only the **pre-engineering** V-010 gate. The pre-release evidence, external sandbox review, V-010 feasibility, independently written second codec, and release permission remain open. This is **not** another engineering authorization, audited architecture change, independent human review, sandbox security finding or release authorization.

## Decision

Freeze [`spec/cddl/plugin.cddl`](../spec/cddl/plugin.cddl) and allocate **additive** W4 registry entries after bridges 53–58. Every added top-level type has `{0: type_id, 1: 1, ...}` and optional key 23 under the preexisting extension rules, uses deterministic OM-CBOR-v1 and rejects CBOR null. No new signature role or primitive is invented.

| Type | ID | Authenticated by | DS-HASH label (where used) | Max encoded bytes |
|---|---:|---|---|---:|
| `PluginPackageManifest` | 59 | SignedEnvelope, **controller** role 1: current plugin publisher keys | `OM-PLUGIN-MANIFEST-HASH-v1` | 65,536 |
| `PluginControlState` | 60 | SignedEnvelope, **controller** role 1: predecessor publisher threshold | `OM-PLUGIN-CONTROL-HASH-v1` | 65,536 |
| `PluginCapabilityGrant` | 61 | SignedEnvelope, **device** role 3: user's issuing device | `OM-PLUGIN-GRANT-HASH-v1` | 16,384 |
| `PluginHostRequest` | 62 | Exact-origin and channel-bound host transport, not a signature | — | 65,536 |
| `PluginHostResponse` | 63 | Host-to-plugin channel direction and binding, not a signature | — | 65,536 |
| `PluginCapabilityCall` | 64 | Host broker requires matching signed, live grant; unsigned itself | — | 16,384 |
| `PluginUiTreeUpdate` | 65 | Host-bound UI-only plugin message; unsigned | — | 49,152 |
| `PluginEvent` | 66 | Host-bound invocation/message; unsigned | — | 16,384 |
| `PluginError` | 67 | Host-bound error message; unsigned | — | 8,192 |

Signatures use the preexisting `DS-SIG` over the canonical body and the new labels `OM-PLUGIN-MANIFEST-SIG-v1`, `OM-PLUGIN-CONTROL-SIG-v1`, `OM-PLUGIN-GRANT-SIG-v1`. Object digests use `DS-HASH` and the table's three hash labels. The fourth hash label, `OM-PLUGIN-CONFIRMATION-HASH-v1`, binds a pending exact send/action and destination, **not** a new signing role or user-consent token. The `Digest` structure and SHA-256 profile are already registered. The 17 capability IDs are exactly the 17 illustrative named capabilities enumerated in [`PLUGIN_AND_APP_EXTENSION_ARCHITECTURE.md`](../docs/architecture/ecosystem/PLUGIN_AND_APP_EXTENSION_ARCHITECTURE.md) § **OM host capabilities**; they are now numbered 1–17, without adding any ambient filesystem, network, key, database, DOM or DeviceVault import. Enums for release/key/grant state, scope, event/message kinds, egress mode, resource-kind, UI kind and error codes are W4-only. Each new field has `"wave": "W4"` in the numeric-field registry.

## Canonical validation and authority boundaries

1. **Byte/profile gate.** Enforce per-type `max_bytes` **before decoding**, plus strict definite-length RFC 8949 CBOR, shortest headers, only unsigned integer keys in typed maps, no CBOR tags, floats, negatives, nulls, invalid UTF-8, duplicate keys or trailing bytes. Reject all unknown/reserved numeric fields. Collections annotated `set` must be sorted by their element's complete canonical encoding and unique; preserve ordered arrays such as UI node lists. Unknown critical extensions fail closed under existing key 23 semantics. W0 receivers must reject **every** type 59–67 as unknown; flag stays off.
2. **Manifest vs grants.** A signed `PluginPackageManifest` declares (not grants) PluginID, release sequence, predecessor release digest, immutable component digests, ABI versions, declared entrypoint/surface pairs, all requested capability IDs, requested exact network origins, resource ceilings and publisher/source metadata. Publisher signature means provenance/update continuity, **not** safety endorsement. An explicit, user-device-signed `PluginCapabilityGrant` is required for **each** installation/capability/scope/expiry; a manifest never confers one. Validate account/device eligibility, approval, install matching, selected-message restrictions and scope policy from authenticated **external** state.
3. **Publisher continuity.** A `PluginControlState` carries random stable 32-byte PluginID, numbered state version, predecessor state hash (absent only at genesis), a unique threshold-governed list of public publisher keys with permanent revoke tombstones and an append-only history of signed-release-record references. Release sequence starts at 1 and appends by one; metadata and manifest hash of an existing release never mutate. Each release can transition `active -> revoked`, never back; keep tombstones. A publisher key is an independently authorized plugin **controller key**, **not** an AccountControlState controller or automatic Room governor. Verify initial publisher trust out of band. For successor states, check the greatest authenticated prior head, hash continuity, prior active signers and prior threshold; reject rollback, forks, key substitution and release resurrection. A release record's ID equals its canonical manifest digest, not a guess from a package URL.
4. **Permission ceiling on update.** `requested_capabilities` may add capabilities in a new manifest: this does **not** make that release invalid, nor does it activate them. `continuity_ceiling` is the intersection-safe, non-expanding automatic carry-forward set. A newly requested capability outside the prior release's set is disabled until the host has a **separately device-approved grant for the new release ID**, after the release was known. A release record trying to automatically expand the prior ceiling is `capability_escalation`. Older explicitly granted capabilities remain bounded by live scope, expiry, policy and revocation. A package update cannot turn on plaintext/history access or network egress by editing its manifest or publisher control state.
5. **Grant revocation.** A grant has stable 16-byte incarnation ID and its own `grant_version`/predecessor grant hash, preserving identity, scope, issuer and validity window across updates; it can move active to revoked and never revive. New authority requires a **new explicit grant incarnation**, not mutating an old grant. Check expiry using authenticated host time and actual active issuer device. A structural device-role signature is not proof the human actually approved the permission.
6. **MessageChannel boundary.** `PluginHostRequest`/`PluginHostResponse` include PluginID, install ID, host-created channel binding, invocation ID, positive per-channel sequence, message kind and a nested complete CBOR payload with a **fixed** type selected by the discriminator. Host checks exact plugin site/origin, channel endpoint and direction **at creation and on each delivery**; a claimed `channel_binding` byte string alone grants nothing. Reject unexpected sequence, origin or channel externally, and reject wrong nested type/IDs, unknown fields and overlong content. Unsigned messages have no authority outside this bound channel. Response policies are **host-authored**; plugin requests cannot assert trusted consent flags.
7. **UI and event isolation.** `PluginUiTreeUpdate` is a bounded flat component tree (at most 128 declarative nodes, one root, no cycles, max depth eight). Events and errors are bounded and tied to an invocation. The host retains ownership of rendering, layout, reserved warning/consent/provenance chrome and action dispatch; these shapes are **not** a script/HTML/DOM language. No wire field lets a plugin suppress safety warnings or author canonical OM events directly. A plaintext trigger taints its invocation.
8. **Per-send confirmation.** `conversation.send_message` (capability 11) is separate from drafting and requires a conversation-scoped grant, exact destination field and a distinct host-confirmed prompt showing destination and **exact outgoing content** every time. The host may report `per_action_confirmed` and a `confirmation_binding` digest only in its own policy response. That digest uses DS-HASH with `OM-PLUGIN-CONFIRMATION-HASH-v1` over canonical `CBOR([plugin_id, installation_id, invocation_id, capability_id, scope, exact_argument_bytes, destination])`. The prompt, decoded content, exact-recipient match, actor eligibility and account-authored event checks occur externally; **a digest or boolean is not itself consent**. Unconfirmed autonomous behavior belongs to a separate `local_component` ServicePrincipal under ADR-0129, never Account-authored plugin events.
9. **Taint/egress.** `content.*` reads and selected-context triggers taint the invocation and data in `storage.plugin_private` (including later reads). Reading does **not** imply network or service-send rights. A tainted invocation cannot use `net.fetch_origin_scoped`, `service.invoke` or any outbound path absent the Room `plaintext_egress` policy, **both** participants' effective signed 1:1 policies, or the strict one-shot user-chosen content/destination/per-action confirmation exception. Continuous/automated plaintext export requires separate Bridge §7 authorization and, in a 1:1, current bilateral signed relationship consent; it is not authorized by a plugin capability grant. `PluginEgressRequest` conveys intent/selected-context reference; the host alone can say whether policy, both consent and manual confirmation were verified. Preserve taint through private storage and refuse unrecognized outward paths.
10. **WIT imports and execution.** Exactly the 17 named illustrative architecture capability interfaces appear as imports, each separately reviewed/host-granted. No WASI, ambient filesystem/network/env/process, OM database, secret keys, DeviceVault, raw DOM or arbitrary FFI. The baseline Component Model world exports `init`, `on-event`, and `render` entrypoints; these names and the stub operation signatures are a conservative first ABI **construction**, subject to later review, not an existing audited stable runtime API. PWA runs only on a **different registrable domain** with COOP/COEP where supported; plugins with `content.*` stay disabled if isolation is unavailable; no same-site fallback. Native runs in a separate process or equivalent memory-isolated host. Wire decoding does not establish any of that.
11. **Bounds are transport/decoder ceilings, not product defaults.** Wire maxima (8 KiB invocation arguments/events; 1 KiB UI/error text; 512-byte destinations/origins; 16 components and ABIs; 32 entrypoints/origins; 8 resource categories; 32 publisher keys; 128 historical releases; 128 UI nodes; 49 KiB nested messages) make accidental or adversarial allocation bounded and produce reviewable objects. The larger 64 KiB control/manifest/envelope maxima account for collections plus signatures. A host may configure stricter memory/fuel/storage/network budgets; **no** operational resource default, permission or pricing/tier is invented by these ceilings.

## Evidence

[`verification/prototypes/plugins-wire/python_codec.py`](../verification/prototypes/plugins-wire/python_codec.py) independently implements deterministic CBOR encode/decode with Python standard library only; it does not import OM's or bridges' codec. `vectors.json` carries **24 positive and 116 negative exact-byte vectors** (140 total), including sender-role checks, typed envelope mismatches, nested null/unknown fields, non-canonical CBOR, unsorted/duplicate sets, object-bound denial, grant/scope/expiry enforcement, manifest-request vs prior ceiling stateful check, publisher/release/grant rollback and fork, tombstone resurrection, ungranted capability calls, per-send confirmation, plaintext-tainted network denial, bilateral 1:1 consent, and **W0 rejection of each nine new top-level types**. `run.py` replays all bytes and requires the exact failure class and registry consistency. Prototype structural signatures are placeholder byte blobs, **not cryptographically valid endorsements**.

This **does not** provide the two independently implemented codecs or the independent reviewer agreement required by the build plan/V-010. It does not prove real signatures/key eligibility, current relationship consents, exact user confirmation UI, runtime taint propagation, origin-bound browser process isolation, limits under hostile wasm, MLS/authenticated event policy, actual accepted release-head gossip, operator domain selection or safe package installation. No code is enabled by this ADR, and no independent review or release authorization is claimed.

## Choices under delegation; no audited design amendment

- **No new signing role.** Existing `controller` (1) is the most conservative match to a publisher's plugin-scoped release-control keys; device grant signatures use existing `device` (3). They provide no native Account control authority. New signature/hash labels only name uses of existing DS-SIG/DS-HASH and SHA-256.
- **Wire ID/shape.** Types 59–67 were the next available contiguous IDs; envelopes contain nested complete canonical CBOR byte strings and explicit direction/kind to close type-confusion channels. No key 13/14 `ConversationEvent` overlay and no new `event_kind` is allocated.
- **Chain genesis and continuity.** Hash-chained grant revocations were added to avoid revocation replay; publisher state genesis and developer provenance require independently pinned trust; a manifest's release ID is its canonical digest (no independent package content tree policy is fabricated).
- **Taint flags.** Only host-origin policy responses contain `per_action_confirmed` and `both_participants_consented`; the wire does not permit a plugin to provide those as authority. Actual remote-origin plaintext disclosure is itself egress and stays denied by default.
- **No defaults.** Budget limits are *requested*, not assigned; origin strings are declarations pending strict origin parsing and policy. WIT methods and UI component kinds are minimal placeholders requiring ABI/runtime review; nothing asserts implementation/platform parity.

## Non-goals and known tension

The build plan's slice 0 requests two independently written codecs while the specified exact deliverable list contains only one Python codec; this artifact follows the exact deliverable list and records the missing second codec as an **open gate**. The architecture calls its capability families *illustrative*, not a finalized published ABI, so IDs and minimal method signatures are an explicit W4 freeze construction, not proof of ABI completeness. The logical package JSON schema permits `previous_release_id: null` and open-ended `resource_limits`, while OM-CBOR-v1 forbids null and this wire must register bounded typed fields; the wire uses **absence** at genesis and a bounded explicit resource-limit set instead. The logical schema's `publisher_proof` is realized as an existing SignedEnvelope, rather than a publisher-supplied arbitrary map that could create a second unsigned authority.

Independent sandbox testing, human review, an independently authored second codec, authorizing plugin deployment/hosting domain, a release toggle and final runtime ABI are expressly outside this freeze. ADR-0259's flag-off and V-010 release gate remain controlling.
