# Checkpoint — 2026-09-29 — Run 7 protocol evolution and engineering-agent guardrails

## Scope

Pre-engineering hardening after Runs 5–6. No product implementation and no human, independent, formal, two-codec or real-LAN verification closure.

## Findings fixed

1. Protocol longevity/extensibility already prohibited silent reinterpretation, but did not give an implementation agent one exact change-class contract. ADR-0162 now classifies normative changes as editorial, behavior-preserving clarification, additive non-critical extension, compatible new profile, security tightening/deprecation, incompatible protocol evolution, or fork/lineage transition.
2. Profile/version ordering was not centralized enough to prevent an implementation from using numeric version/profile IDs as security ordering. Selection is now `security_generation`-first per conversation type; deprecated candidates are avoided for new traffic when an equal-or-higher non-deprecated candidate exists; equal-generation ties use the smallest profile ID only as a deterministic tie-break.
3. Extension version evolution could still be interpreted as allowing criticality/schema changes in place. A published `(extension_id, version)` is immutable, extension-ID criticality is immutable, `!` IDs are permanently critical, and authority/security/ownership/fallback changes require a new extension ID and/or CryptoProfile.
4. Engineering handoff rules did not explicitly force an agent to preserve old published meaning and classify changes before editing normative material. The machine policy, validator and AGENTS/engineering handoff rules now prohibit the common shortcuts.
5. The portable phase-1 runner now includes the ADR-0162 bounded evolution harness and supports bounded producer ranges so long runs can be completed without pretending a wrapper timeout was a test failure.
