## Architecture decisions closed

1. ACTIVE accepted 1:1 mailbox/relay deposits under CryptoProfile 1 use mandatory `SealedDeliveryEnvelope`; there is no silent clear-sender fallback.
2. The sealed wrapper contains the complete unchanged ordinary inner 1:1 envelope. Successful outer HPKE open is routing privacy, not sender authentication; existing relationship, ACS/device, PQXDH and Double Ratchet checks remain authoritative.
3. Recipient devices advertise route-specific delivery material with signed `SealedDeliveryKeyRecord` objects delivered inside the accepted relationship. Large hybrid delivery keys are not embedded per device × relay in `RelaySet`, avoiding a hidden RelaySet/device-count ceiling.
4. `MessageRequestPayload.reply_delivery_key` is a required, request-scoped bootstrap key for the one first post-acceptance sealed response; first contact itself still uses the IntroGate/MessageRequest admission boundary.
5. CryptoProfile 1 sealed delivery reuses the pinned reviewed draft-ietf-hpke-pq-05 base-mode `MLKEM768-X25519` / HKDF-SHA256 / ChaCha20Poly1305 suite with distinct sealed-delivery domain labels, exact 1216-byte public keys, exact 1120-byte encapsulations and fixed plaintext/ciphertext buckets.
6. Every new seal gets a fresh random 128-bit `delivery_id`. Recipients reserve `(delivery_key_id, delivery_id)` durably before inner plaintext release/ack; exact-wrapper same-route retry is allowed, while changing routes requires the route-specific key, fresh HPKE sealing and a fresh delivery ID.
7. Established mailbox-class metadata descriptors expose neither stable sender/device identity nor Double Ratchet header shape by design. Timing, padding bucket, source-network metadata, volume and opaque route/key identifiers remain explicitly declared residual leakage.
