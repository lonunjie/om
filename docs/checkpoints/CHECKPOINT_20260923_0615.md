## What this pass settled

This pass jointly attacked ordinary messenger completeness and Groups → Rooms → Communities because their event and authority semantics overlap.

### Ordinary messenger baseline

`MESSENGER_BASELINE_V1.md` now classifies first-release expectations as core interoperable semantics, standardized optional capabilities, local/account-private UX or deliberately later features.

Important boundaries include:

- shared room pins are protocol state; personal bookmarks are local;
- moderator redaction is distinct from author deletion;
- V1 polls have deterministic vote state but do not claim cryptographic voter anonymity;
- voice notes are typed encrypted audio attachments, not a second transport;
- forwarding creates a new destination event and does not leak private source IDs by default;
- scheduled send remains an encrypted local-device queue until actual send;
- calls remain separate ephemeral/session state rather than durable chat correctness state.

### Interactive Room identity

The previous architecture carried both `GroupID` and `ConversationID` for the same private group. Current architecture removes that redundancy:

```text
interactive Room/private group identity = ConversationID
```

That ConversationID is bound into group-control/MLS context. “RoomID” is a product/architecture term, not another mandatory wire ID.

### Space / Community architecture

A `Space` is a provider-independent organizational/control container. “Community” is ordinary-user presentation, not a second object class.

Space links can contain independent Rooms, Publications and nested Spaces. Joining a Space does not silently join/decrypt child Rooms. Official affiliation is bilateral so a malicious Space cannot falsely claim an independent Room/creator.

A Room may use Space membership/role as admission evidence and may explicitly delegate selected management powers to at most one authority-parent Space in the baseline. Delegated authority is materialized in authenticated Room control state rather than becoming invisible transitive permission magic.

### Roles, permissions and governance

Capabilities are the authority primitive. Roles are named bundles.

OM does not require numeric role hierarchy, a universal Administrator bypass or a permanent magical owner. Explicit restrictions subtract authority and delegation ceilings stop a role manager from granting powers outside its own authorized grant scope.

High-risk changes can require quorum. If governance is irrecoverably lost without a pre-authorized succession path, the object becomes administratively frozen rather than giving SeedLife/providers a hidden takeover key.

### Threads and Topics

Conversation organization is layered:

```text
reply -> lightweight same-Room thread -> persistent room-local Topic -> independent Room
```

Topics do not get separate membership or MLS state. Forum mode can require a Topic for top-level conversation while normal chat remains the default.

### Broadcast

Private announcement channel = ordinary private MLS Room with `room.post` restricted to publishers.

Public one-to-many = separate signed `Publication` object with optional independent discussion Room. Followers are not canonical Publication members. OM does not invent a second massive-private-broadcast cryptosystem in V1.
