## Numbered findings

1. **Conflict · High — Bridge control heads and quorum evidence.** ADR-0269, Decisions 2–3, requires Core to verify signed observations and refuse quorum-dependent actions without verified approvals. ADR-0270, Decisions 1 and 5, requires the bridge offer to use a verified head and preserve admission checks. Bridge proposal and admission do not consult the verified Room chain. The admission reducer counts proposal-reported approvers toward quorum. The service offer path checks the held head and withholds unverified approvals. `crates/om-wasm/src/bridge/scope.rs:1309–1356`, `crates/om-core/src/bridge_room.rs:155–191,262–279`, `crates/om-core/src/service_offer.rs:229–253`. [ADR-0269](../../decisions/ADR-0269-room-service-control-head-observation.md), [ADR-0270](../../decisions/ADR-0270-bridge-offers-and-review-targets.md)
2. **Conflict · High — Room mutations lack a Core-validated capability basis.** ADR-0271, Decisions 3 and 8, permits an injected source of the member's capabilities and keeps authorization in Core. The scoped-permissions design requires effective grants and restrictions to be authenticated and scoped. The bridge and service Room commands accept a capability set at the engineering API boundary and apply protected mutations against it. The connected service offer's head check authenticates the service state and leaves the caller's Room authority unchecked. This is confined to the scoped reducer interface at the reviewed revision. `crates/om-wasm/src/bridge.rs:1467–1509`, `crates/om-wasm/src/bridge/scope.rs:899–939,1025–1048,1216–1262,1345–1365`. [ADR-0271](../../decisions/ADR-0271-engineering-host-service-adapters.md), [Scoped permissions, “Capability model” and “No ordinary-role deny maze”](../architecture/groups/SCOPED_PERMISSIONS_AND_CONVERSATION_ORGANIZATION.md), [Privacy, Governance, and Authority, “Core authority rule”](../constitution/PRIVACY_GOVERNANCE_AUTHORITY.md)
3. **Conflict · High — Bridge approval can outlive the reviewed offer.** ADR-0270, Decisions 3–4, requires a replacement offer to invalidate the earlier target. The bridge reducer can replace an observation while retaining the same target, and it retains no separate incarnation check against the removed membership. The service proposal path explicitly rejects changed observations that reuse a target and rejects reuse of the removed incarnation. `crates/om-core/src/bridge_room.rs:108–121,203–225,251–296`, `crates/om-core/src/service_offer.rs:128–169`. [ADR-0270](../../decisions/ADR-0270-bridge-offers-and-review-targets.md), [Scoped permissions, “Immutable reduction incarnation”](../architecture/groups/SCOPED_PERMISSIONS_AND_CONVERSATION_ORGANIZATION.md)
4. **Conflict · High — Bridge freshness uses mixed clock sources.** ADR-0269, Decision 4, requires monotonic runtime observation time. The signed observation and query use the generic Core clock, whose Wasm host default is wall time. The bridge handle separately uses supplied time readings for admission and freshness, while the host adapter compares the projected age with a separately injected bound. The reference path lacks an enforced common runtime segment for that decision. Calendar expiry in invocation review is a separate clock class. `crates/om-core/src/engine.rs:1551–1623`, `packages/om-core-wasm/src/wasm.ts:36–50`, `crates/om-core/src/bridge_room.rs:189–200,331–356`, `apps/web/src/host/scope/bridge.ts:98–108,185–191`. [ADR-0269](../../decisions/ADR-0269-room-service-control-head-observation.md), [Time and expiry, §§1–3](../architecture/events/TIME_AND_EXPIRY_SEMANTICS.md), [ADR-0154, Decision 1](../../decisions/ADR-0154-verifier-timer-runtime-segments-and-web-verifier-liveness.md)
5. **Gap · High — Verified revocations do not reach the Room membership reducer.** ADR-0129, Decision 6, requires a verified revocation to stop sends and queue endpoint removal. The signed observation updates the profile-scoped chain and its projection. The service and bridge membership reducers retain independent held heads and pending-removal state. The signed observation path does not propagate the accepted change to those reducers. This review established a missing integration in scoped state. `crates/om-core/src/engine.rs:1551–1593`, `crates/om-core/src/service_room_member.rs:155–205`, `crates/om-wasm/src/bridge/scope.rs:933–966,1247–1254`. [ADR-0129](../../decisions/ADR-0129-extension-service-and-client-trust-boundaries.md), [ADR-0269](../../decisions/ADR-0269-room-service-control-head-observation.md)

## Recommended fixes

- Use verified, profile-bound Core state for Room capabilities, quorum, signed heads and bilateral affiliations. Carry accepted endpoint reductions into the membership reducer and apply reader visibility to private projections.
- Use a single monotonic runtime clock for bridge freshness. Bind offers to the full reviewed instance and preserve the required bridge and service labels in the resulting views.
- Wire a profile-private engineering host entry and durable operation receipts. Return results for the exact request, including after restart, and convey the defined unsupported actions honestly.
- Bind invocation review to the exact Core-checked selection and disclosure policy. Expose Core retention classification through the public export projection and state evidence exclusions explicitly.
- Exercise both positive and negative release builds, including the separate service-worker graph, in the checked-in release guard suite.
