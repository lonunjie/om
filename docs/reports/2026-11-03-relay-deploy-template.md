## What was built

| Piece | Where |
|---|---|
| **Template skeleton** (what the per-user repository contains) | [`infra/cloudflare-home/release/template/`](../../infra/cloudflare-home/release/template): [`package.json`](../../package.json) (`cloudflare.bindings.OM_ADMISSION` is the one prompt; `build` and `deploy` run the verifier first), [`wrangler.json`](../../infra/cloudflare-home/release/template/wrangler.json) (the four SQLite Durable Objects, `no_bundle`, no R2/KV/D1/Queues, no logs), `.dev.vars.example` (makes `OM_ADMISSION` a Worker secret, so it survives redeploys), `.node-version` (24: ML-DSA needs it), exact-pinned `wrangler` with `pnpm-lock.yaml`, README, AGPL-3.0-or-later LICENSE (finding 1), [`SECURITY.md`](../../SECURITY.md) |
| **Verifier** (the template's first step) | [`release/verify-relay.mjs`](../../infra/cloudflare-home/release/verify-relay.mjs) (shipped in the template as `verify.mjs`) plus [`verify-chain.mjs`](../../infra/cloudflare-home/release/verify-chain.mjs), a byte copy of the web release verifier (symlink in the source tree), so the **same pinned 2-of-3 offline root, delegation and ML-DSA-65 co-signature** govern web and relay releases |
| **Signed relay release** | [`release/build.mjs`](../../infra/cloudflare-home/release/build.mjs): bundles the audited Worker with `wrangler deploy --dry-run` (deterministic, 76 KB, no third-party code in it), writes `relay-manifest.json` (`om.relay-release/1`: file hashes, the signed deploy configuration, commit), signs it with the delegated release key (`--sign-from-vault`), adds `SHA256SUMS`, an in-toto/SLSA `provenance.intoto.jsonl` and the owner's pin `release.lock`, then verifies the result. `--compare <dir>` rebuilds the Worker from a checkout and compares bytes |
| **Tests** | [`test/template.test.ts`](../../infra/cloudflare-home/test/template.test.ts): 29 cases with throwaway keys and roots. Build and verify; shipped CLI rejects any other root; 17 tamper cases (changed byte, extra file, added R2, changed migration, logs on, build command, deploy script without verifier, added dependency, version range, [`wrangler.toml`](../../deploy/cloudflare-pages/wrangler.toml), `.npmrc`, replaced verifier, SUMS, version bump, wrong pin, no provenance, no lock, changed lockfile); unsigned, wrong roots, expired delegation, rollback floor; malformed `OM_ADMISSION`; a `wrangler deploy --dry-run` from the template uploads the released bytes unchanged with exactly four Durable Objects; the released Worker in workerd advertises `om.admission.v1`, refuses creation without the setup key and carries a message with it. The **whole existing Home suite also passes against the released bytes** (`OM_HOME_BUNDLE=<worker.js> pnpm exec vitest run infra/cloudflare-home`: 107 passed) |

How it meets PROVISIONING_AND_BOOTSTRAP section 10: (1) what is activated is a signed release pinned by digest (`release.lock` pins the manifest digest; the manifest pins the Worker's); (2) the template's first step is a verifier, there is no application build, a branch head is never deployed (`no_bundle`, and the deploy script stops if the verifier fails); (4) the verifier is itself in the signed manifest. The owner pins the root: it is in [`verify-chain.mjs`](../../infra/cloudflare-home/release/verify-chain.mjs), which the owner can replace for their own distribution.

## Findings from the full design read (all recorded; none silently resolved)

1. **Licence mismatch, pre-existing; decided 2026-11-03 (operator: "decide based on the design").** [`LICENSING_AND_CONTRIBUTION_POLICY.md`](../constitution/LICENSING_AND_CONTRIBUTION_POLICY.md) section 1 and [`LICENSE.md`](../../LICENSE.md) put reference relay, provider and **provisioning** software under **AGPL-3.0-or-later**: it exists to be run as a service, so the network boundary must not let a hosted derivative close its source (section 3), while the protocol stays implementable by anyone under Apache-2.0 artifacts (section 4). [`REUSE.toml`](../../REUSE.toml) and the file headers had mapped `infra/**` to MPL-2.0 with no ADR behind it. The design wins: the template, the builder, the verifier and the template test are now AGPL-3.0-or-later (SPDX headers, a [`REUSE.toml`](../../REUSE.toml) override, [`tools/om_registry.py`](../../tools/om_registry.py), the template's `LICENSE` and [`package.json`](../../package.json), and a README section that points to the corresponding source and says the bundled MPL-2.0 files stay MPL-2.0, combined as MPL-2.0 section 3.3 allows). **Not changed:** the relay Worker source (`infra/cloudflare-home/src`, `packages/om-home-wire`) still carries MPL-2.0 headers while the design says AGPL for the relay; it was published under MPL-2.0 since 2026-10-29 and another session is editing those files, so a coordinated header change (and the section 8 note that released versions keep their licence) is a follow-up for the operator.
2. **D15 and D16 depart from ADR-0130 rule 2** (staged update controller, verification against TUF targets metadata rather than this OM-specific manifest, a verifier that can vouch for itself). They are recorded as deviations, with no ADR written over audited text; the operator should accept or waive them explicitly. The relay manifest reuses the web release's proven chain rather than TUF targets/snapshot/timestamp roles, as the web release already does.
3. **Fail-open admission** (now fixed, decision 3 below) conflicted with the extensibility rule "refuse rather than continue with weaker semantics" and with the fail-closed zero-budget principle; the read supports making the Worker fix.
4. **Custody not in place.** Before the template repository is published: custody-map entry (the repository, its verifier releases; no project OAuth client is used by this path), mirror, owner of the GitHub organisation, [`SECURITY.md`](../../SECURITY.md) (added to the template; the advisory feed of PR-012 is not set up).
5. **Release gates unchecked.** I did not declare this release in [`machine/repository_contract.json`](../../machine/repository_contract.json) or check the applicable public-release gates (PR-001, PR-005, PR-012, PR-013); the validator blocks a declared public release with an open gate. Publishing the template is such a release.
6. **Copy added to the template README:** operator statement and no warranty, one account is one observer (METADATA_THREAT_MODEL wording), trust on first use for a workers.dev address, a lone relay is a single failure domain, passkey advice, stale clones hear of no advisory, delegation expiry does not stop a running relay. Not added: `export_migration_state()` for the provisioning method, the `OM_WAKE` default and usage/budget display (the relay reports quota itself).
7. **Vendor naming:** HOME section 7 keeps vendor names out of the main flow; ADR-0186 decision 2 names Cloudflare for this option, which the onboarding session handles. The Git-account requirement belongs to that same page.

## Deviations and gaps (recorded as D14..D18 in the relay status report; no ADR over audited text)

- **D14** Deploy-to-Cloudflare needs a GitHub or GitLab account and a public repository.
- **D15** The staged update controller of PROVISIONING section 10 rule 3 / CLIENTHOST section 4 is **not built**: updating is manual (replace the release files, run the verifier). No independent transparency monitors (single-operator digest log, as for web); the relay release is not yet appended to `deploy/release-log`. The delegation expires **2027-01-26**: after that a stale clone's build fails closed until a newer template is taken.
- **D16** The verifier inside the template cannot vouch for itself (rule 4: "its verifier is itself a signed, pinned release"). It is signed and pinned, and an independent copy from a `lonunjie/om` checkout checks it (README), but a compromised template repository could replace both. Mirroring and custody of the template repository are not set up.
- **D17** Setup value as a secret, open if empty or malformed (decision 3 above); the build cannot see Cloudflare secrets.
- **D18** No CycloneDX SBOM for the relay release: the bundle holds only Worker and `om-home-wire` code (checked: no `node_modules` path in it). The deploy tool `wrangler` is exact-pinned with a lockfile in the template, resolved from npm at build time; this is a build-time dependency of the deploy step, not of the deployed code.

**Untested against the real service (assumptions to confirm on the first real deploy, which needs the operator's approval):** that Workers Builds honours `.node-version` 24 (without Node 24 the post-quantum check fails closed and nothing deploys), that the setup page shows the `cloudflare.bindings` description for a `.dev.vars.example` secret and stores it as a Worker secret, that it leaves [`wrangler.json`](../../infra/cloudflare-home/release/template/wrangler.json) untouched apart from `name`, and that `wrangler deploy` of a `no_bundle` single-file Worker with Durable Object migration `v1` succeeds on a fresh account (the dry run does).
