# Own-relay onboarding: the operator's flow mapped onto the audited design

- **Date:** 2026-11-03
- **What this is:** the operator described the onboarding they imagine (page 1 explains "you own your data, not us", then the person sets up their own relay and storage on Cloudflare, with other methods later; lean free-tier defaults; the one-click deploy belongs to each user, not the website repo; each person's `*.workers.dev` address is their discovery address, secured against spam from the first use). This report maps it onto the audited design, marks where the design already says it, where it says something different, and where it is silent. **No code and no deploy.** Conflicts are for the operator to rule on.
- **Terminology:** the operator calls it the relay. The design's word for relay + key pool + discovery publisher + first-contact gate run together is "Home" (the 2026-09-24 hardening review, ADR-0102); the operator did not coin it and people never see it (UI says "delivery service"). Below I say "relay" and write "Home" only when quoting the design.
- **Design sources read:** [`HOME_ONBOARDING_TIERS_AND_PROVIDER_DIVERSITY.md`](../architecture/providers/HOME_ONBOARDING_TIERS_AND_PROVIDER_DIVERSITY.md) (sections 2, 3, 4, 5, 6, 7, 8), [`PROVISIONING_AND_BOOTSTRAP.md`](../architecture/providers/PROVISIONING_AND_BOOTSTRAP.md) (1 to 9, 10), [`CLOUDFLARE_REFERENCE_DEPLOYMENT.md`](../architecture/providers/CLOUDFLARE_REFERENCE_DEPLOYMENT.md) (all), [`DISCOVERY_AND_ONBOARDING.md`](../ux-design/specs/DISCOVERY_AND_ONBOARDING.md) (UX spec, all), [`INVITES_INTROGATE_AND_SPAM.md`](../architecture/discovery/INVITES_INTROGATE_AND_SPAM.md) and [`DISCOVERY_FABRIC.md`](../architecture/discovery/DISCOVERY_FABRIC.md) (earlier today), [`HARDENING_REVIEW_20260924.md`](../reviews/HARDENING_REVIEW_20260924.md) (sections 5 and 6), ADR-0102, ADR-0112, [`home-api.md`](../../spec/protocol/home-api.md) (admin and capability parts), [`PROVIDER_CONFORMANCE_SUITE.md`](../architecture/providers/PROVIDER_CONFORMANCE_SUITE.md) (PC-C lines), `limits.ts`. **Not read:** [`INVITE_AND_EMPTY_STATE.md`](../ux-design/specs/INVITE_AND_EMPTY_STATE.md), [`SOFTWARE_SUPPLY_CHAIN_AND_UPDATES.md`](../architecture/providers/SOFTWARE_SUPPLY_CHAIN_AND_UPDATES.md) (template verifier, TUF), [`CLIENTHOST_UPDATE_LIFECYCLE.md`](../architecture/client/CLIENTHOST_UPDATE_LIFECYCLE.md), [`PROJECT_STEWARDSHIP_AND_CONTINUITY.md`](../constitution/PROJECT_STEWARDSHIP_AND_CONTINUITY.md) section 5 (custodied assets), [`UI_UX_SYSTEM.md`](../architecture/ux/UI_UX_SYSTEM.md) onboarding section, ADR-0021, [`STORAGE_AND_BLOB_ARCHITECTURE.md`](../architecture/storage/STORAGE_AND_BLOB_ARCHITECTURE.md). ## 2. Where the operator's flow differs from the design: your ruling needed

1. **R2 ("storage").** The audited baseline is Worker + SQLite Durable Object and says "do not require R2": R2 needs a subscription and a payment method even for the free allowance, so "the baseline 'set up OM without entering a card' path must not depend on R2" (`CLOUDFLARE_REFERENCE_DEPLOYMENT`, "Why R2 is not mandatory"; `PROVISIONING` section 6). R2 is an optional BlobStore for large offline attachments and backups. *Recommendation:* the one-click sets up the relay only (free, no card); R2 becomes an opt-in step later ("add storage for big files and backups", with a plain note that Cloudflare asks for a card). The chat-history backup file already works without any storage. Tell me if "storage" meant something else.
2. **Own relay first vs sponsored first.** ADR-0102 made a **T0 sponsored starter mailbox** (from the inviter's relay, no signup) the default first-run path because requiring a cloud account first fails the "person who cannot configure Wi-Fi" test (R-010). The hardening review (section 5, item 1) left "own cloud first" as the alternative for the operator to choose; ADR-0112 records only "start with Cloudflare". Your flow is the "own cloud first" alternative, which is yours to choose. Needs: a recorded operator decision (an ADR in the ADR-0112 style, "Decided by: operator", not one an agent writes on its own authority), and an answer to whether a person invited by a friend still gets the no-signup path as one of the choices on that page.
3. **Vendor names.** Audited section 7: "No vendor names or infrastructure vocabulary appear outside Advanced". Your page names Cloudflare as the first method. *Recommendation:* the choice reads "Set up my own, free" and the method name sits behind "More options"/Advanced, as the 2026-11-02 "never say Home" rule did.
4. **The default relay baked into the signed build** (SeedLife's, commit 771e088) is the opposite of this flow and of "nobody relies on us". Under your flow it goes away when the page exists; until then the product has no other way to work. Your decision on when.
5. **The one-click button in the website repo.** Today `lonunjie/om.lonunjie.org/README.md` points the button at that repo's `release/`, which deploys a **static copy of the web app** (a ClientHost) from a branch, not a relay. Two departures from the design: it is not the per-user relay setup you describe, and it breaks R-261 ("every provisioning method deploys a signed, digest-pinned release verified against TUF; none builds from a mutable branch"). Taking it out of the site repo is right. A push to that repo's `main` is a production deploy of om.lonunjie.org, so I will not touch it without your approval; I will prepare the change on a branch for preview. A replacement template (a verifier + the relay release) is a custodied asset (`PROJECT_STEWARDSHIP` section 5) in a repo of its own. Where it lives is your call.

## 3. Where the design is silent: questions, not inventions

- **"Secure the address the first time."** The audited text covers spam in depth (adaptive IntroGate controls, reserved capacity for invite-bound tickets so people you invited always get through, ticket limits: `INVITES_INTROGATE_AND_SPAM` 4 to 8 and 11) and says each provider uses its own front-line defenses (section 8: the relay protects delivery queues, the IntroGate protects first contact). It is **silent on binding a freshly deployed relay to its owner**. Today, queues, key pools and descriptor ids are claimed by whoever uses them first (deviation D3): between deploy and the owner's first call, anyone who knows the `workers.dev` address could claim the owner's mailbox or descriptor id. Needs a design answer, e.g. a deploy-time owner secret the client generates and the template stores as a Worker secret, which the relay checks for the first claim. That adds a requirement the design does not state, so it needs your yes before I design it.
- **The IntroGate is built in the relay but Core never calls it** (D10). Spam protection on the personal address therefore exists only in the Worker; it starts to matter when invites carry the introduction service (the first-contact plan).
- **Cloudflare Tunnel, opening ports and firewalls, Docker image, install script:** nothing in the audited documents I read. T3 says "VPS, home server or single-board computer" and the static-binary reference target. These are methods of the future second relay, not part of the Cloudflare path. They would be added under `ProvisioningMethod` without changing anything else.
- **Lean defaults and limits.** The audited text requires limits that are advertised and typed (PC-C01) and a free-plan budget that sheds before the hard stop, but fixes no numbers ("implementation parameters, not protocol constants"). The relay's current defaults are in `infra/cloudflare-home/src/limits.ts` (queue 512 items / 16 MiB, 7-day retention, 64 deposit capabilities, descriptor 32 KiB, and so on) and were written for a shared multi-person Home, not for one person's relay. For a personal relay the sane profile is smaller: one owner, a handful of mailboxes, no host console or per-member quotas, no logs, no R2/D1/Pages/KV, wake channel on (idle cost near zero, measured today), slow poll when hidden. The Cloudflare free-plan limits to size against must be checked on the day. Proposed: derive a `personal` limits profile from the free plan numbers with a documented safety margin and a usage counter that warns before the hard stop (PC-C03 `ProviderUsageState`, unbuilt, D12).
