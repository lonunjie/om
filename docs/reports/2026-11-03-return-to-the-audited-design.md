# Returning to the audited design: what drifted, what did not, and how to stay on it

- **Date:** 2026-11-03
- **Asked by the operator:** why a new ADR, when the v1 design is complete, audited several times, and the coding agent only has to follow it; and how to get back to the audited approach.
- **Short answer:** a new ADR is the wrong tool. The audited design already says what to build; the departure is ADR-0181 section 2.1 and the implementation deviations D1 to D12, all written during engineering. The way back is to implement the audited text, record anything that still differs as a deviation (never as an amendment), and have the operator review the few decisions below. The "link format" ADR proposed in [`2026-11-03-first-contact-across-homes-plan`](2026-11-03-first-contact-across-homes-plan.md) is withdrawn.
- **Design sources read for this report:** [`DISCOVERY_FABRIC.md`](../architecture/discovery/DISCOVERY_FABRIC.md), [`INVITES_INTROGATE_AND_SPAM.md`](../architecture/discovery/INVITES_INTROGATE_AND_SPAM.md), [`CONTACT_SHARING.md`](../architecture/discovery/CONTACT_SHARING.md), [`KEY_TRANSPARENCY_AND_DIRECTORY.md`](../architecture/discovery/KEY_TRANSPARENCY_AND_DIRECTORY.md), [`MULTI_RELAY_AND_DELIVERY_RESILIENCE.md`](../architecture/delivery/MULTI_RELAY_AND_DELIVERY_RESILIENCE.md) (1 to 6), [`RELAY_AND_DELIVERY_ARCHITECTURE.md`](../architecture/delivery/RELAY_AND_DELIVERY_ARCHITECTURE.md) (the Cloudflare section and conformance list), [`spec/protocol/home-api.md`](../../spec/protocol/home-api.md) (opening and section 3), [`spec/cddl/discovery.cddl`](../../spec/cddl/discovery.cddl) and [`delivery.cddl`](../../spec/cddl/delivery.cddl), [`PROVISIONING_AND_BOOTSTRAP.md`](../architecture/providers/PROVISIONING_AND_BOOTSTRAP.md) 2 and 10, ADR-0019, 0032, 0043, 0181 (sections 1 to 3), 0183 (header), 0184 (header), [`2026-10-28-relay-status.md`](2026-10-28-relay-status.md) (deviation table D1 to D12). **Not read:** ADR-0181 sections 4 onward, ADR-0184 and 0185 bodies against [`IMPORT_EXPORT_AND_USER_ESCAPE.md`](../architecture/ecosystem/IMPORT_EXPORT_AND_USER_ESCAPE.md), [`NOTIFICATIONS_AND_PUSH.md`](../architecture/client/NOTIFICATIONS_AND_PUSH.md) in full, [`ASYNC_KEY_MATERIAL.md`](../architecture/crypto/ASYNC_KEY_MATERIAL.md), ADR-0126 and 0142 to 0147. ## 1. What "audited" means here

The baseline is the design as it stood at `design_open=0` with the engineering authorizations (ADR-0169, 0171, 0172, 0177): everything under `docs/architecture/`, `spec/`, and the ADRs up to 0177. I cannot independently verify the audits; I take the operator's statement and the ledger (ADR-0167 records the review model). Everything decided after that baseline is the only place drift can come from: ADR-0178 to 0180 (operator direction), and ADR-0181 to 0185 plus the deviation table, all written by engineering agents under delegation.

Most of the shipped product follows the audited text (first-contact cryptography, hidden requester, symmetric binding, sealed delivery). The drift is concentrated where the engineering agents went alone: **how two people on different Homes find each other and deliver**, plus the default-Home and backup decisions.

## 3. The way back

1. **No new ADRs for design-bound work.** An agent never amends audited text, with or without "operator delegation". If code and audited text disagree, the code is wrong. If the text looks wrong or incomplete, the agent writes a question in a report and stops. Anything that ships differently goes in the deviation table with the audited passage it departs from, as D1 to D12 already do. This is now rule 6 of the Design gate in [`AGENTS.md`](../../AGENTS.md).
2. **Operator review of the five decisions that came from agents**: ADR-0181 2.1 (mark superseded), the default Home in the signed build, ADR-0184, and, for completeness, ADR-0183 and ADR-0185 (both already consistent). A different-vendor read is the strongest check (ADR-0167 recorded the earlier single-vendor model as a compromise).
3. **Restore, in this order, straight from the audited text** (the detail is in the first-contact plan, with decision 1 there replaced by this report's row 1): the invite and descriptor carry `introduction_services[]` and the IntroGate flow (rows 1 and 2) -> deposit to the route's Home, poll your own (row 3) -> relationship fetch capabilities and spec key shapes (row 4) -> a second RelaySet entry with failover and usage state (row 7) -> move to own Home -> Deploy-to-Cloudflare template -> second vendor-neutral Home -> sponsorship.
4. **Keep the gate.** Every code commit lists the design domains it read and its departures ([`tools/design_gate.py`](../../tools/design_gate.py), `make hooks`). A departure with no accepting record blocks the commit.
5. **Nothing else changes in the meantime**: no new features, no ADRs, no spending. The wake channel and the backup file stay as shipped, labelled.

## 4. Where I (this session) went wrong, so it is on record

I wrote a delivery plan before reading the discovery design; proposed a Paid plan against the constitution; wrote an ADR for a wake channel the audited Cloudflare profile already permits, without citing that profile; and then proposed another ADR to patch the invite instead of asking why the invite lost its locator. The first three are corrected in the reports; the fourth is withdrawn here.
