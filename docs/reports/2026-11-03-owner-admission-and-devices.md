# Owner admission for a personal relay, the shareable address, and one person's devices

- **Date:** 2026-11-03
- **Asked by the operator:** is binding a new relay to its owner part of the design; decide the best design; keep the address from being world-announced, with expiry and usage limits and anti-spam; could several devices of one person be "logged in" through the same Cloudflare account, and is that against or with the design?
- **Design sources read:** [`home-api.md`](../../spec/protocol/home-api.md) sections 1 to 3.2 and 4 to 6, [`PROVISIONING_AND_BOOTSTRAP.md`](../architecture/providers/PROVISIONING_AND_BOOTSTRAP.md) (all), [`CLOUDFLARE_REFERENCE_DEPLOYMENT.md`](../architecture/providers/CLOUDFLARE_REFERENCE_DEPLOYMENT.md), [`INVITES_INTROGATE_AND_SPAM.md`](../architecture/discovery/INVITES_INTROGATE_AND_SPAM.md), [`DISCOVERY_FABRIC.md`](../architecture/discovery/DISCOVERY_FABRIC.md), [`MULTI_DEVICE_SYNC.md`](../architecture/crypto/MULTI_DEVICE_SYNC.md) (all except the verification tail), [`HOME_ONBOARDING_TIERS_AND_PROVIDER_DIVERSITY.md`](../architecture/providers/HOME_ONBOARDING_TIERS_AND_PROVIDER_DIVERSITY.md) sections 4 to 6. **Not read:** [`ASYNC_KEY_MATERIAL.md`](../architecture/crypto/ASYNC_KEY_MATERIAL.md), [`ENDPOINT_COERCION_AND_PLATFORM_LEAKAGE.md`](../architecture/client/ENDPOINT_COERCION_AND_PLATFORM_LEAKAGE.md), the multi-device plan, ADR-0141 and ADR-0021 beyond what the documents above quote.

## 1. Is binding the relay to its owner in the design?

The capability model is; the bootstrap is not. [`home-api.md`](../../spec/protocol/home-api.md) sections 2 and 3.2 say routine provider administration uses **resource-scoped opaque capabilities**: at least 256 random bits, scoped to one provider and one resource or operation family, independently rotatable, never reused across providers, never requiring AccountID, carried in the `Authorization` header or the operation's CBOR slot and never in a URL. How a freshly deployed relay learns who its owner is, is not specified. The shipped relay creates a queue, descriptor or key pool for whoever asks (deviation D3), so a stranger who learns the address can fill the owner's free quota. (My earlier report said a stranger could *claim the owner's* mailbox. That was overstated: every claimable id is 128 random bits the stranger cannot know. The real exposure is open creation.)

**Decision (the operator asked me to decide; recorded as D13, an implementation of the audited capability model, not an amendment):** an **admission capability** for the operation family "create resources on this relay".

- The client makes 32 random bytes for that one relay. The relay is deployed holding only `SHA-256("OM-RELAY-ADMISSION-v1" || secret)` as a public variable (`OM_ADMISSION`, several allowed); the secret never leaves the client and is not in any repository or template.
- When hashes are configured, four owner-side operations need the secret in the `om-admission` header: create a queue, publish or delete a descriptor, publish a key bundle, issue intro tickets. Everything a peer does (deposit, drain and ack with their own capabilities, key fetch, first-contact submission, reading a public descriptor) needs nothing. A wrong or missing secret is the same `unauthorized` as any bad capability (no oracle). The relay advertises feature `om.admission.v1` only when configured, so a client knows to send it; a relay without hashes behaves as before (shared or test Home).
- One departure from [`home-api.md`](../../spec/protocol/home-api.md) 3.1, stated plainly: the header is custom (`om-admission`) because `Authorization` already carries the resource capability on those operations. It travels over the same HTTPS, is never in a URL, and falls under the same no-store, no-referrer and log-redaction rules.
- Built and tested (workerd): `infra/cloudflare-home/test/admission.test.ts`, PC-X01 to PC-X07. The client side (generating, storing and showing the setup code during onboarding) is part of the onboarding page.

## 2. The address should not be world-announced

This is already the audited behaviour, and nothing needs adding. A public directory entry "should publish an `IntroductionServiceDescriptor`, not a static mailbox capability" and is meant for public figures (`INVITES_INTROGATE_AND_SPAM` 4). What a person shares is an **invite**: a scoped rendezvous capability with `expires_at`, optional `max_uses`, revocation independent of every accepted relationship, single-use tickets with a payload limit and anti-replay nonce, and reserved capacity so people they invited always get through while strangers are rate-limited (sections 2, 3, 5, 6, 11). The relay's `workers.dev` address is a **locator, never AccountID** (ADR-0032), carried inside the invite; no public contact page is needed, and I will not build one. Descriptor ids are 128 random bits, so the descriptor is reachable only by those given the invite.

## 3. One person's devices and the Cloudflare account

- **Logging in to Cloudflare on several devices to be "logged in as me" is against the design.** A provider account is never identity: "a Home is a replaceable bundle of provider capabilities, never account authority" and "AccountID is not a bearer credential" ([`home-api.md`](../../spec/protocol/home-api.md) 1); "Cloudflare-specific identifiers never enter canonical identity" (`CLOUDFLARE_REFERENCE_DEPLOYMENT`, `PROVISIONING` 8); the hosting account is part of the *endpoint trust base*, which is why the design asks for a passkey on it (`HOME_ONBOARDING` 5, R-164). Identity is the cryptographic AccountID, and a new device joins only by an explicit grant from an existing device; it "never approves itself", and every link notifies every other device (`MULTI_DEVICE_SYNC`, R-166). A Cloudflare login would make Cloudflare an identity authority.
- **Sharing one relay among one person's devices is with the design.** Every device is a first-class endpoint with its own routes and delivery keys on the relay the person runs (`MULTI_DEVICE_SYNC` "Delivery"; RelaySet is per relationship).
- **How a second device gets onto the relay:** the account-private sync channel explicitly *excludes* "provider capabilities/deployment credentials" (`MULTI_DEVICE_SYNC`), so the admission secret must not be synced. A second device needs its own scoped, expiring, single-use admission handed over *inside the approved link ceremony*. The design is silent on that operation, and Core does not implement the ceremony yet (`2026-11-02-multi-device-plan`), so it is deferred, and the relay already accepts several hashes for it.
