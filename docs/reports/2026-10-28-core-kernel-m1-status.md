- **Date:** 2026-10-28
- **Scope:** `core_kernel` (ADR-0169). Authors: Claude Sonnet 5.5 subagents (pass 1 and pass 2, same day). A Claude Opus audit follows; ADR-0167 still requires a non-Anthropic reviewer of the crypto adaptations.
- **Goal:** the real OM Core as Rust crates compiled to WASM, behind the same typed boundary as the dev harness (task C1 in [`2026-10-11-reference-client-ui-first-web-tasks.md`](2026-10-11-reference-client-ui-first-web-tasks.md)).

## Design as built

- **No storage and no network inside Core.** Every mutating call stages a transaction and returns a `Commit` (one atomic record write per profile, so a single `EncryptedKv.put` is a whole transition). State and effects are released only after the host acknowledges the commit (`finish_commit(id, true)`). A refused write discards the stage: no outcome, no plaintext and no network effect existed.
- **Persisted outbox.** Network work is listed from state (`net_ops`), identified by a stable id, and survives restart. `Unavailable` keeps `PendingNetwork`; a `Timeout` after a deposit is `PendingReconciliation` and is retried with the same envelope bytes and the same operation id; a relay redelivery is deduplicated, not reported as an integrity failure.
- **Profile namespacing.** One record per profile in that profile's encrypted store, no shared identifier. A context captured before close, reopen or restart is stale (per-boot nonce in the generation) and fails closed with an error, not an outcome.
- **Outcome classes** are exactly those in the contract. Destructive intents without a confirmation token are `Rejected(unauthorized)`.
- **First contact (pass-1 shape).** Inviter publishes an invite descriptor to the introduction service; the link `om:invite/<80 bytes base64url>` commits to the invite id, the ACS head hash and the request-key digest, so the service cannot substitute either. The invitee verifies, pins the inviter's ACS head, and deposits a W0 `MessageRequest` (validated by `om-codec`) HPKE-sealed with the pinned draft-ietf-hpke-pq-05 suite. The inviter sees an `IntroductionRequest`, pins nothing and can decrypt nothing until `AcceptIntroduction`; then the inviter fetches the invitee's key material, runs PQXDH and sends the first session message. The relationship context is mandatory for every inbound session envelope (ADR-0137).
- **Dependencies added:** none beyond the V-001/V-005 prototype set (RustCrypto, dalek, libcrux ML-KEM/ML-DSA, `getrandom` custom backend on wasm32). New non-crypto crates: `serde`, `serde_json`, and dev-only `flate2` (rust backend, to read the gzipped corpus) and `proptest`. No new crypto dependency, so nothing here needs operator approval.

## Spec questions and deviations from pass 1 (status after pass 2; none resolved silently)

1. **Resolved in pass 2** (canonical events, see below). Original pass-1 note: **Messages are not yet `ConversationEvent`s.** [`EVENT_MODEL.md`](../architecture/events/EVENT_MODEL.md) defines canonical events with EventIDs; pass 1 carries an internal payload (`kind 1` text, `kind 2` hello) inside the ratchet and dedupes by a sender-chosen 128-bit message id. Highest priority for pass 2, because it changes what is signed, stored and synced.
2. **Resolved in pass 2** (sealed-sender delivery, see below). Original pass-1 note: **No sealed-sender wrapping.** The relay sees the sender's `EncodeEC(IK_A)` and the ratchet header on every envelope (the prototype envelope shape). `delivery.rs` (ADR-0142) is ported and vector-checked but not wired because per-relationship delivery-key exchange and its lifecycle are not built. Security-relevant metadata gap; record before any release.
3. **Partly resolved in pass 2**: states are now signed and chained and the V-002 verifier is in CI; the link ceremony, peer head refresh and recovery are not built. Original pass-1 note: **AccountControlState is the unsigned one-device body of the V-001 prototype.** No controller signatures, no `AccountControlHead`, no generation chain, so "the pinned ACS head" is a hash of an unsigned body. The invite link authenticates it for first contact; real continuity needs `om-control` and the formal-model CI coverage the constitution requires.
4. **First contact is not the full IntroGate flow.** Not built: signed `ContactDescriptor` with an intro identity, `IntroductionTicket`, signed `MessageRequestPayload`, `IntroIdentityBinding`, admission proofs. The link commits to the ACS head and request-key digest instead of the spec's "request key trusted only when signed by the intro identity", and `ticket_id` carries the invite id. Spec question: may an invite link commit to the request key digest directly, or is an intro-identity signature mandatory even for invite links? Pass 1 chose the stricter-than-spec-silent reading (nothing is accepted that the link does not commit to) but it is not the specified object set.
5. **Who initiates the session after acceptance.** The spec says both sides establish PQXDH sessions; pass 1 has the accepting inviter initiate exactly one and the invitee answer on it. Simultaneous-initiation policy is V-003 territory and is not exercised.
6. **Invites are single-use.** The first valid request marks the invite used (conservative; `max_uses` per IntroGate is unmodelled). A hostile first requester can burn an invite; real rate and admission controls are IntroGate work.
7. **Recovery key.** [`RECOVERY_AND_BACKUP_POLICY.md`](../architecture/identity/RECOVERY_AND_BACKUP_POLICY.md) calls for a 256-bit checksummed key plus locator, but no display format. Pass 1 shows 56 base32 characters (32 random bytes plus a 3-byte check) in 14 groups of 4. Core does **not** retain the RecoveryRoot after display and does not bind it to a `RecoveryPolicy` commitment, so recovery cannot be performed yet. `GetRecoveryStatus` therefore reports `policy: "pending"` and never `on`.
8. **Partly resolved in pass 2**: `receipt.update` events are accepted and settle `Delivered`; Core never *sends* receipts (no privacy-policy input yet). Original pass-1 note: **Delivery receipts.** `DeliveryState.delivered` needs a receipt event the spec does not define for 1:1; outgoing messages stop at `sent`.
9. **Partly resolved in pass 2**: one-time prekeys are replenished; signed-prekey rotation and bundle renewal are not. A retried `FetchKeyMaterial` can still consume a second one-time prekey. Original pass-1 note: **Prekey housekeeping.** Bundles carry a 90-day `expires_at` but there is no republish/rotation timer and no one-time-prekey replenishment; after the first 10 each are consumed the signed last-resort keys are used (the ledger covers that path). A retried `FetchKeyMaterial` can consume a second one-time prekey.
10. **Wall-clock use.** `Clock` feeds display timestamps, invite and bundle expiry hints only. Peer-supplied `sentAt` is shown as given and orders nothing.

## Pass 2 (what changed, in the order worked)

1. **Sealed-sender delivery (security-relevant, done first).** Every established 1:1 deposit is now a W0 `SealedDeliveryEnvelope` (type 23) around the unchanged inner PQXDH/ratchet envelope; the relay sees no sender IK, ratchet header, DeviceID, AccountID or ConversationID (`crypto/delivery.rs`, `flows.rs`). Signed `SealedDeliveryKeyRecord`s (type 22) travel inside the relationship (Hello and a new `Keys` control message). A request-scoped bootstrap key rides in the MessageRequest payload, admits at most 8 distinct wrappers (ADR-0146) and only the peer's Hello, and is destroyed in the same transaction as the winning Hello (ADR-0145). Replay state is `(delivery_key_id, delivery_id)` with exact-wrapper fingerprints; because inner acceptance and `COMPLETE` are one staged transaction, `RESERVED` never becomes durable (a refused host commit simply re-delivers). There is no clear fallback: a send without an established key is *queued* (never sealed to the bootstrap key, never clear) and goes out when the peer's signed record arrives. Evidence: `tests/sealed_delivery.rs`, `tests/w0_conformance.rs`.
2. **Canonical ConversationEvents.** Messages are W0 type-10 events (EventID, HLC, ConversationID, principal, endpoint) built and checked by `events.rs`; the inner payload discriminator is the object type. Inbound events must name this conversation and be authored by the pinned peer endpoint; dedupe is by EventID; one EventID with two payloads rejects every version. `edit` and `delete` (author-only, clock-ordered) and `receipt` (settles `Delivered`) are applied; `reaction` is accepted with no state; later-wave kinds are refused. ConversationID is chosen by the inviter and carried in its authenticated Hello. Evidence: `tests/sealed_delivery.rs` (`mod events`).
3. **Signed AccountControlState (`control.rs`).** `authorize` is a port of the V-002 mirror and is checked in CI against the 63 committed golden vectors, the machine-readable transition policy, and (locally, `OM_ACS_EXHAUSTIVE`) all 16,200 cases of the Python enumeration ([`verification/bounded/acs_dump_cases.py`](../../verification/bounded/acs_dump_cases.py)): 16,200 of 16,200 agree. Genesis and every successor are `SignedAccountControlState`s (controller-role signatures verified against the credentials the state commits to, parent chaining, parent-evaluated authorization); invites and requests carry and verify the whole chain and the link still pins the head hash. `GetDevices` is derived from the head. `SuspendDevice` and `RevokeDevice` are real transitions. Evidence: `tests/acs_authorization.rs`, `tests/devices.rs`.
4. **Prekey replenishment.** A low one-time-prekey inventory republishes a fresh batch (same epoch, same bundle). Evidence: `tests/prekeys.rs`.
5. **Web wiring (C1).** `apps/web` production now runs the real Core (`apps/web/src/core/RealApp.tsx`): `om_wasm.wasm` is a hashed build asset (so it is in the signed bundle manifest), profile vaults and `EncryptedKv` are the storage, identities are listed in a tiny IndexedDB registry, and the shell is shared with the dev entry. **No provider adapter exists**, so production runs with none and says so ("Not connected to a provider", queued locally). A separate build (`pnpm --filter @om/web build:core-e2e`, `VITE_OM_E2E_CORE=1`, directory `dist-core-e2e`) uses the in-page TEST loopback provider under a loud banner; the production bundle check refuses its marker and the test-support module. One UI contract fix: invite creation and invitation acceptance now wait for a settled outcome (`settledOutcome`), because the real Core reports `PendingNetwork` first. Evidence: `apps/web/e2e/core.spec.ts` (two identities in one browser: invite, introduction, messages both ways, relay sees only sealed objects, reload and unlock restore history; passes in Chromium, Firefox and WebKit), `apps/web/e2e/production.spec.ts`, `landing.spec.ts`.

## Spec questions and security-relevant decisions (pass 2)

- **Sealed delivery needs a route, and Core has no RelayEntry/RelaySet yet.** The route binding uses the fixed route name `om-core:mailbox/v0` plus the mailbox capability (`CORE_ROUTE_URI`). It still binds a key to one deposit capability, but it is not the spec's `relay_uri`. Revisit when RelaySet lands.
- **Delivery-key lifetime.** Keys live 90 days; a wrapper lives 7 days and never past its key; the bootstrap key lives 7 days. There is no key rotation timer yet: an expired peer key makes sends fail closed (`Unavailable`) rather than fall back.
- **Retry reseals.** `RetryDelivery` reseals the stored inner envelope under a fresh `delivery_id`; the recipient dedupes the inner envelope. (An in-outbox retry resends the exact wrapper.)
- **Invite links vs signed objects (question 4, now answered by the spec).** [`INVITES_INTROGATE_AND_SPAM.md`](../architecture/discovery/INVITES_INTROGATE_AND_SPAM.md) section 5.1 says a sender uses a request key *only from a signed object* (the ContactDescriptor signed by the intro identity). Pass 1/2 instead pin the request-key digest in the link. That accepts nothing the link does not commit to, but it is **not** the specified object set; do not treat first contact as conformant.
- **AccountControlState scope.** Only transitions that one local controller can authorize are executable (`link_messaging`, `quarantine`, `remove_messaging`, single-controller `revoke_control`). A transition that needs other controllers' signatures answers `Rejected(unsupported)` because there is no signature-collection transport; recovery votes count as zero. The verifier itself implements every row, including freeze resolution and fork bridge (vector-tested).
- **Safe-by-default consequences of an unbuilt link ceremony.** `OfferDeviceLink`, `RequestDeviceLink`, `ApproveDeviceLink`, `RejectDeviceLink`, `StartRecovery` and `VetoRecovery` stay `Rejected(unsupported)`. Linking a device without multi-device session fan-out (ONE_TO_ONE_SESSION_MANAGEMENT.md) and peer ACS refresh would create a "linked" device that no contact can reach, which is worse than refusing. Peers do not yet refresh a pinned ACS head, so a revocation does not reach contacts.
- **Hash-chain evidence uses the credential list in the invite.** A peer verifies the chain against the credentials the descriptor supplies; each signer must be the credential the state itself commits to.
- **Flagged for the audit:** the ACS parser now rejects any ACS key outside 0..=14 (critical extensions such as `om.acs.fork_ack` and `legacy_policy` live in key 23 and are unsupported, so such states are rejected as the spec requires of a decoder that lacks them).
- **Test-only code in `om-core`:** `debug_app_state`, `debug_inject_payload`, `debug_link_messaging_device` and `LoopbackNetwork` exist only under `test-loopback` (excluded from `production` by a compile error and by [`tools/core_guard.py`](../../tools/core_guard.py)).

## What remains

1. IntroGate object set (question 4 above): signed `ContactDescriptor` with intro identity, `IntroductionTicket`, signed `MessageRequestPayload`, `IntroIdentityBinding`, admission proofs; `ShareContact`, `BlockPerson` with provider scope, `ChangePrivacyPolicy`. Invites remain single-use.
2. Device linking, multi-device session fan-out, peer ACS-head refresh and `AccountControlHead` gossip; signature collection for majority transitions; `RecoveryPolicy` commitment, RecoveryRoot custody, `StartRecovery`/`VetoRecovery`; the continuity assessment. `GetRecoveryStatus` still reports `pending`.
3. Signed-prekey rotation and bundle expiry renewal (they change the epoch and the provider pool, which the provider contract does not yet express); delivery-key rotation; `RelayEntry`/`RelaySet`.
4. Per-conversation records and operation-log compaction (state is still one record per profile, which keeps every transition a single atomic `EncryptedKv.put`; a batch API is needed first).
5. A real provider adapter (reference Home is `provider_reference` scope) so production is connected; until then production says it is not.
6. Consolidate the two CBOR codecs; fuzz targets under `fuzz/`; `conformance/` runner; wasm size and startup measurements against the V-022 budgets (the wasm is about 2.6 MB); a second CryptoProfile-agility test.
7. Independent review of the crypto adaptations (ADR-0167): the code is adapted from prototypes written by a Claude agent and reviewed by Claude only. The new `control.rs` verifier and the sealed-delivery acceptance path are also Claude-only.
