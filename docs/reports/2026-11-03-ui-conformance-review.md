## 2. Method and limits

- **Build under test:** the production entry (`ConfiguredApp`) built from the working tree at `f3e0cf4` with `VITE_OM_RELAY_URL=http://127.0.0.1:8788 VITE_OM_ALLOW_LOOPBACK_RELAY=1 OM_BUNDLE_DEV=1` into a scratch directory, served by `vite preview`, talking to the repo's local reference Home (`infra/cloudflare-home/test/serve.ts`, workerd). This is the same fixture `make web-e2e` uses for the relay specs. The repo's own `dist-*` folders were stale (built 08:03, before 0.0.10 at 09:07) and were not touched. Every screenshot carries the loud brown **E2E LOCAL RELAY** banner, which exists only in this test build; a production bundle does not show it.
- **Browser:** Chromium from the shared Playwright cache (`@playwright/test` 1.63.0). Nothing was installed.
- **Flows driven:** separate browser contexts (separate storage) for Alice, Bob, Carol, Dana and Eve: landing, first run, invite ready, QR, paste, Bob opening Alice's link and accepting, Alice's message request, accept, chat both ways, an offline send, block confirmation, an existing user opening an invite link, Settings and each subpage, the safety-code flow, a password vault reload (Unlock), dark appearance, reduced motion, keyboard focus, 320 px reflow, 200% root text, forced colors.
- **Screenshots:** 390x844 and 1280x800 of each state, 84 files. They are not committed (binary); they are in the shared notes folder `side-session-notes/local_b1ca610a-c92e-4a33-a71f-2f22dec600f0/ui-conformance-shots/`, with names like `20-settings-menu-390.png`.
- **Not exercised:** the camera scanner dialog, the profile switcher with two identities in one browser, a failed send ("Failed . Retry"), the stranger-pressure notice, the install handoff of an invite, the service worker and update prompt, dark appearance on every screen (one chat only was captured in dark), screen-reader output, real devices, motion recorded as video (only the tokens and the reduced-motion computed values were read). Latency budgets (V-022) and comprehension (V-018) remain open design gates and are out of scope.
- **Verdicts:** *conforms*, *departs* (the shipped thing differs from audited text), *unbuilt* (audited text asks for it, it is not there), *silent* (the audited documents I read do not say).

## 3. Summary for the operator

The table in section 4 has 58 rows (counts in its closing line). The ones that matter most:

1. **The Omnibar does not exist.** It is the audited find-or-do surface and the way the design reaches everything that is not a tab. Nothing in the shell opens it, Ctrl/Cmd+K does nothing, and the `AppShell` slot for it is unused (S4).
2. **After the first chat there is no way to invite or scan.** The invite screen only appears while the chat list is empty (S5). The audited design keeps Invite reachable through the Omnibar, People, conversation actions and a scanner action ([`INVITE_AND_EMPTY_STATE.md`](../ux-design/specs/INVITE_AND_EMPTY_STATE.md) section 7); none of those exists. This is a functional dead end, not a style point.
3. **The shipped "OM Calm" is not the audited OM Calm palette**, and the focus colour is blue where the spec reserves violet (V1, V2). ADR-0179 says the web client was built with the same palette; the generated tokens show otherwise.
4. **Chat rows carry no preview, unread, draft or pending marker** (L1), and the conversation has no header actions (call, details, search) and a composer with only a field and Send (C1, C2).
5. **Outgoing bubbles are solid cobalt**, against the audited "tint, not a saturated block" rule (C3). The destructive "Yes, block" is a blue primary button, not the protected red (V4).
6. **Settings is a different tree** from the audited one: Lock, Backup file, Help and Message delivery exist; Profile, Privacy and protection, Notifications, Appearance and Advanced do not (S8).
7. What is solid: the Chats-only compact root with no one-item tab bar, the trailing lower profile control, the invite-first empty state in substance, the message-request card with its "Unverified" label, non-colour-only status cues, reduced motion, 320 px reflow, large text, forced colours, 44 px targets on the one screen measured, and plain, calm copy.

## Applied (2026-11-04)

The operator ruled the audited design wins. Answers to section 6 and what was done (commits on `main`, trailers carry all four design domains, `Design-Departures: none`):

1. Omnibar and new conversation (S4, S5): built (tap and Cmd/Ctrl+K; local, deterministic, no message search or learning yet) with the Sheet pattern and edge-swipe Back.
2. Palette and focus (V1, V2): the audited OM Calm values replaced the shipped palette via tokens; a test compares the CSS to [`om-theme-clear-v1.json`](../ux-design/tokens/om-theme-clear-v1.json). Success and warning backings are derived tints. The audited `border.strong` is about 2.3:1 on the light canvas (below 3:1).
3. Outgoing bubble (C3): tint. 4. Block confirmation and explainer (V4): red only for failure or destructive, green only for success or verified.
5. Chat rows (L1): identity, latest message, time, unread, draft. The preview is built in TS from `GetConversationView`; Core's list has none and no Rust changed. Core keeps no read state: unread uses a local encrypted last-seen marker (deviation).
6. Wide rail (S2): removed; the redundant "Chats" pill is gone. 7. Invite choices (F3): Share invite link, Scan QR code, Show my QR.
8. Section 5: kept and recorded as deviations: name at setup, web-link invite fragment, Settings search, Lock, Backup, Help, per-device idle lock. Removed: golden-section card, brand header, red-dot and safety-code card styling, slide-in panes, "round everything".
9. Delivery page (T5, F6): tier, observer, migration and origin facts added; raw address behind a disclosure. When an address is in use and Core's tier is still "none", the "not picked yet" line is omitted (Core does not derive the tier from the configured address; gap for a Core change).

Still open: message search and learning in the Omnibar; tier and origin choices (the facts are shown, not yet choosable); `border.strong` contrast.
