# Identity validation and freeze gates

This specification defines the minimum evidence required before OM freezes a public identity mark or wordmark.

## Gate I1 — silhouette survival

Pass deterministic tiny-size, monochrome, platform-mask, tinted/themed, and notification/favicons checks. **R11C/R12 status: static pass for shortlist; not sufficient alone.**

## Gate I2 — unprimed association

People who did not design the mark must describe what they see **before** candidate names/rationales are revealed. Record unwanted associations and brand confusion.

## Gate I3 — findability in clutter

Test the mark in realistic app grids at actual sizes. Measure time-to-find and misses after the participant knows the target. Synthetic browser tests are preparation only; physical launcher testing is required before freeze.

## Gate I4 — delayed recognition/memory

After intervening tasks, test whether participants can recognize the mark among plausible decoys. Do not optimize around exact-detail recall; the coarse silhouette should carry identity.

## Gate I5 — name/mark fit

Test the mark with `OM` and any proposed long-form word mark. A strong symbol does not rescue a confusing/unavailable name, and a name should not be chosen merely to explain a weak symbol.

## Gate I6 — platform parity

Verify actual iOS/iPadOS/macOS appearances, Android adaptive/themed launchers, PWA install/home surfaces, favicon/browser surfaces, and notification/status uses. Platform materials may differ; core visual features must remain stable.

## Gate I7 — accessibility/inclusion

Mark recognition must not depend on hue, animation, translucency, or one background. Check increased contrast and system tinting. Avoid culturally/religiously loaded appropriation; OM does not use the sacred `ॐ` symbol.

## Gate I8 — similarity/name legal review

Before public freeze, run qualified trademark/name/visual-similarity clearance in intended jurisdictions/classes. R12 public-web reconnaissance is a warning system only, not clearance.

## Gate I9 — evidence-backed geometry freeze

No candidate geometry is changed merely to create novelty between revisions. Once testing begins, geometry changes require a documented issue and trigger retesting.

## Current R12 state

- **One Thread / Open Loop / Peer Link:** advance to blinded human/device testing.
- **Dialogue Fold / OM Fold:** controls unless new evidence justifies revival.
- **Final mark:** not selected.
- **Public long-form name:** not cleared.
