# OM Canonical Event Model — Gate B Selected Direction

- **Status:** Canonical pre-engineering architecture; logical schemas remain draft
- **Timestamp:** 2026-09-23 07:56 PHT
- **Goal:** A small transport-independent vocabulary that every OM client, UI, bridge, relay integration, and future transport can project into.

## Decision summary

OM uses an **immutable event model with materialized local views**.

The network protocol does not transmit UI widgets or database rows. It transmits a small set of semantic events. Edits, reactions, deletes, and receipts are new events referencing earlier events.

The core deliberately separates:

1. **content events** — durable conversational user actions;
2. **control state** — identity/group/device authority, owned by the corresponding protocol;
3. **ephemeral signals** — typing/presence-like hints, never required for correctness;
4. **local state** — mute, personal bookmark, archive, draft, scroll position, local delete, search index;
5. **transport provenance** — SMS/RCS/bridge/provider information that does not redefine message semantics.

This avoids one giant event taxonomy.

## Why immutable events

Immutable events make:

- offline creation easy;
- multi-device synchronization easier;
- retries idempotent;
- edits/deletes auditable as state transitions;
- transport adapters simpler;
- local database repair possible;
- materialized UI views replaceable.

OM does **not** require an unbounded permanent event log. Clients may compact local event history once equivalent state and policy requirements are satisfied.

## Core identifiers

### ConversationID

Random, provider-independent conversation identifier.

A provider URL, phone number, room server, or username is never a ConversationID.

For a private OM group, `ConversationID` is bound to the group identity.

For a 1:1 relationship, it is established with the RelationshipBinding.

### EventID

Generated by the originating client without server coordination.

Selected direction:

- 128 bits of cryptographically secure randomness;
- opaque;
- no embedded account, relay, or provider identity.

Collision probability is negligible for the intended use while keeping identifiers small.

### EventClock

OM needs deterministic display/merge ordering without a global sequencing server.

Selected direction: a **Hybrid Logical Clock (HLC)** value generated/updated by clients.

Conceptual tuple:

```text
physical_ms
logical_counter
endpoint_tiebreak
```

Properties:

- approximately follows human wall-clock time;
- remains monotonic when clocks move backward;
- can deterministically order concurrent events;
- does not create a centralized sequencer.

The entire native event is E2EE, so the relay need not observe this value.

A misleading client clock can make its own messages appear oddly positioned but does not grant identity or authorization.

## Native event envelope

Logical shape:

```text
ConversationEvent
  protocol_version
  event_id
  conversation_id
  author_principal            # typed PrincipalRef: account | service | bridge
  author_endpoint_id          # authenticated credential endpoint under that principal
  clock
  kind
  kind_version
  required_capabilities[]
  body
  representation?             # ServicePrincipal acting under scoped RepresentationGrant
  foreign_provenance?         # BridgePrincipal foreign-network attribution/fidelity
  expiry?
```

For OM-native E2EE, the secure session/MLS layer authenticates the endpoint credential that sent the event and binds it to `author_principal`. For an account author the endpoint is an authorized `DeviceIdentity`; for a service author it is an authorized service endpoint; for a bridge author it is an endpoint authorized by `BridgeControlState`.

The envelope therefore does not force automation or foreign-network actors to masquerade as an AccountID. OM classifies protocol authority rather than attempting to detect human-vs-AI cognition. Account, service and bridge endpoint credentials remain different authority classes: neither service nor bridge endpoints count in `AccountControlState` device-majority governance.

A ServicePrincipal acting on behalf of an AccountPrincipal may attach a valid `representation` reference, but canonical authorship remains the service. A BridgePrincipal carrying a foreign message attaches `foreign_provenance`; foreign display identity is bridge-attested metadata rather than native Account authorship.

### No mandatory per-message durable signature

OM-native messages SHOULD NOT require a separate long-lived digital signature on every message when the secure session/group protocol already authenticates the sender.

Reasons:

- less overhead;
- simpler key handling;
- avoids accidentally creating stronger durable non-repudiation than intended;
- mirrors the security boundary of modern secure messaging protocols.

Control documents that require durable signatures use their own signed formats.

## Baseline durable event kinds

Keep v1 deliberately small.

### `message.create`

```text
message.create
  content?: RichTextV1
  attachments[]
  reply_to?
  thread_root_event_id?
  topic_id?
  mentions[]
  expires_after?
```

Rules:

- `content` uses bounded semantic `RichTextV1` when present; plain text is represented as a single Paragraph/Text run;
- HTML/CSS/JavaScript/Markdown are not authoritative wire formats; formatted paste/Markdown-like composition is locally sanitized into RichTextV1;
- no active rich-text execution or embedded web content is permitted;
- large binary data is never inlined into the event;
- `reply_to` and `thread_root_event_id` MUST reference events in the same ConversationID;
- `topic_id`, when present, is room-local organization rather than a new encryption context.

### `message.edit`

```text
message.edit
  target_event_id
  replacement
```

Only the same author principal, or an explicitly authorized moderator where policy permits a distinct moderation action, may alter shared state. Ordinary author edits are bound to the original author principal; moderation remains `moderation.redact` rather than pretending the moderator is the author.

Concurrent edits resolve deterministically using authenticated authorization plus EventClock ordering.

Clients may preserve edit history locally.

### `message.delete`

```text
message.delete
  target_event_id
  reason?
```

This means "request/tombstone this message for the shared conversation state."

OM must not promise remote physical erasure after a recipient has already decrypted or exported content.

"Delete for me" is local state and is not a network event.

### `reaction.set`

```text
reaction.set
  target_event_id
  reaction_key                 # Unicode token or canonical custom-reaction token
  reaction_asset?              # ExpressiveAssetRef when custom
  present: true | false
```

Reaction state is keyed by:

```text
(actor_principal, target_event_id, reaction_key)
```

Unicode reactions remain the zero-dependency baseline. A custom reaction carries an inert `ExpressiveAssetRef` plus fallback semantics from [`EXPRESSIVE_MEDIA_CONTENT_PACKS_AND_ENTITLEMENTS.md`](../ecosystem/EXPRESSIVE_MEDIA_CONTENT_PACKS_AND_ENTITLEMENTS.md); the immutable BlobID is the rendering authority, not a live pack/catalog. The latest authorized state wins.

This makes adding/removing a reaction idempotent and multi-device friendly.

### `receipt.update`

Batched receipt information.

```text
receipt.update
  receipt_type: delivered | read
  event_ids[]
```

Receipts are optional policy/capability features.

Group read receipts may be disabled by default to reduce traffic and privacy leakage.

Relay delivery acknowledgement is not necessarily the same semantic thing as "human read."

### `pin.set`

Shared room pins are durable authorized state:

```text
pin.set
  target_event_id
  present: true | false
```

A personal bookmark remains local/account-private state.

### `moderation.redact`

```text
moderation.redact
  target_event_id
  reason?
```

This is an authorized moderator action against another principal's content. It is distinct from `message.delete`, so the protocol never pretends the original author performed a moderator removal. Remote physical erasure is not guaranteed.

### Polls

V1 standardizes convergent poll semantics using:

```text
poll.create
poll.vote
poll.close
```

The `poll.create` EventID identifies the poll. Latest authorized vote state per `(actor_principal, target_poll_event_id)` wins; close is monotonic and reorder/duplication convergence is a verification obligation. Baseline polls do not claim cryptographic voter anonymity; see [`MESSENGER_BASELINE_V1.md`](MESSENGER_BASELINE_V1.md).

### Topic organization

Persistent room-local topic state uses standardized capability-gated operations:

```text
topic.create
topic.update
topic.status.set
message.topic.set
```

Topics organize a Room but do not create another membership/MLS object. Lightweight threads use `thread_root_event_id` and require no separate event kind. See [`SCOPED_PERMISSIONS_AND_CONVERSATION_ORGANIZATION.md`](../groups/SCOPED_PERMISSIONS_AND_CONVERSATION_ORGANIZATION.md).

### Forwarding is new authorship

A private forward/resend is a new `message.create` authored by the forwarding account. Private source ConversationIDs/EventIDs/AccountIDs are not carried across conversation boundaries by default. Public signed Publication posts may carry public source provenance.

## Control state is not ordinary chat content

Do not duplicate authoritative identity or group policy inside arbitrary chat events.

Examples:

- AccountControlState;
- device authorization/revocation;
- GroupState;
- MLS membership epochs;
- recovery-policy transitions.

The UI may project these authoritative transitions into timeline notices:

```text
Alice added a phone.
Bob left.
Carol removed Dave.
```

but the authoritative source is the corresponding control protocol.

This prevents the chat log and the security state from disagreeing.

## Ephemeral signals

Examples:

```text
typing.start
typing.stop
presence hint
live activity hint
```

These are best-effort frames, not durable ConversationEvents.

They:

- may be dropped;
- are not backed up;
- are not required for state convergence;
- have short TTLs;
- should be aggressively rate limited.

## Local-only state

Never make the relay/network store these merely because the UI needs them:

- draft text;
- mute;
- personal bookmark / saved-message marker;
- archive;
- local labels/folders;
- scroll position;
- local delete/hide;
- search index;
- theme;
- UI layout;
- scheduled-send queue before the message is actually sent.

Shared room pins are **not** in this list; they use `pin.set`. Private multi-device preference sync can be designed later as account-private encrypted sync.

## Attachments

Messages reference encrypted blobs rather than containing them.

Logical descriptor:

```text
AttachmentRef
  blob_id
  media_type
  plaintext_size
  ciphertext_digest
  encryption_descriptor
  locations[]
  filename?
  dimensions/duration?
```

Rules:

- random opaque blob identifiers;
- client-side encryption before upload;
- multiple locations may point to mirrored ciphertext;
- storage providers do not define message identity;
- recipient may re-home the blob into its own StoragePool;
- attachment metadata that is privacy-sensitive stays inside E2EE content.

Blob/locator semantics are frozen by the 2026-09-23 storage/repair resolution; operational retention defaults remain policy.

## Size/resource limits

Lean default:

- maximum baseline event envelope: **64 KiB**;
- binary media always external;
- clients SHOULD batch receipts and acknowledgements;
- extensions count against the same size ceiling.

A future capability may raise limits, but the baseline protocol remains cheap to parse and reject.

## Extension model

OM core has a small permanent vocabulary.

An event may carry:

```text
required_capabilities[]
extensions{}
```

Rules:

1. Unknown optional extensions are ignored/preserved only when safe.
2. If a required capability is unknown, show an unsupported-content placeholder rather than misinterpreting it.
3. Extensions cannot silently gain identity, crypto, storage, or device-authority privileges.
4. Extension data counts against normal resource limits.
5. A widely adopted extension may later become a standardized OM capability without changing old events.

Namespace recommendation:

```text
org.example.feature-name
```

Registry/governance follows the accepted public registry and extension criticality rules.

## Transport adapters

Transport is outside conversation semantics.

```text
SMS/RCS/XMPP/etc.
      ↓
TransportAdapter
      ↓
ConversationEvent + provenance
      ↓
local materialized conversation view
```

### Local imported transports

An Android SMS adapter can normalize an SMS into the local event model.

Transport provenance is stored with the local event record:

```text
source_transport
remote_message_id?
security_class
adapter_id/version
```

The adapter cannot claim OM-native E2EE.

### Network bridges

A bridge that crosses another network is an explicit OM principal/trust boundary.

If plaintext is exposed at the bridge, the UI/security state must show that.

## Materialized views

Clients should not render the raw event log directly.

Maintain derived views such as:

```text
ConversationList
MessageTimeline
ReactionState
ReceiptState
UnreadState
SearchIndex
AttachmentIndex
```

Views can be deleted and rebuilt from canonical local state.

This allows third-party UIs to organize the same protocol data differently.

## Storage model

Recommended local architecture:

```text
encrypted local database
  ├── canonical events/control records
  ├── materialized views
  ├── attachment metadata
  └── local-only preferences
```

Search indexes remain local unless a user explicitly chooses another encrypted design.

## Compaction

Immutable does not mean infinite.

Clients may compact:

- superseded reactions;
- obsolete receipts;
- ephemeral delivery bookkeeping;
- materialized intermediate state;

once equivalent state is safely represented and backup/audit policy allows it.

Do not compact away security-critical control history needed to validate AccountControlState, GroupState, recovery, or transparency chains.

## Gate-B adversarial/interop tests

1. same event arrives three times;
2. edit arrives before original message;
3. delete arrives before original;
4. two devices edit one message concurrently;
5. reaction add/remove is reordered;
6. missing receipt batch arrives later;
7. clock moves backward by hours;
8. malicious client sends 10 MB "text" event;
9. unknown optional extension arrives;
10. unknown required extension arrives;
11. SMS and OM-native messages coexist in one UI;
12. bridge message declares weaker security;
13. attachment has three provider locations and one fails;
14. event database materialized views are deleted and rebuilt;
15. offline devices merge events in different arrival orders and converge.

## Gate-B exit criterion

Two independent clients given the same authenticated events/control records in different delivery orders must converge on the same semantic conversation state, apart from explicitly local presentation choices.

## 2026-09-21 addendum — calls and future carrier adapters

Call negotiation/media state is ephemeral control state and is not added to the baseline durable conversation event vocabulary. A local call-history UI may materialize a separate local record.

SMS/MMS/RCS remain transport provenance/adapters added later; they do not change canonical OM-native event identity or semantics.

## 2026-09-22 engineering refinement — RichTextV1

`message.edit.replacement` follows the same RichTextV1 semantic model. Protocol encoding uses the OM deterministic-CBOR profile and bounded node/text/url counts. Unknown future rich-text node kinds follow explicit extension criticality; clients must always be able to produce a safe plain-text fallback for supported content.
